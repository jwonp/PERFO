# 부하테스트 이론 정리 — 티켓팅 API 실측과 매핑

> 이 문서는 부하테스트의 개념·지표·방법론을 정리하고, 각 항목을 이번 티켓팅 API 실측([`01_RESULTS_SUMMARY.md`](01_RESULTS_SUMMARY.md))에서 실제로 어떻게 했는지 연결한다. "무엇을 왜 어떻게 봤는가"의 근거 문서.

## 1. 부하테스트란

시스템에 **의도적으로 부하를 걸어** 성능 특성과 한계를 측정하는 것. 목적은 두 갈래:

1. **정합성 검증** — 동시성 하에서 데이터가 깨지지 않는가 (오버셀, 중복, 음수 재고). "빠른가"보다 우선.
2. **성능 특성 파악** — 얼마나 빠른가(latency), 얼마나 견디는가(throughput/한계), 어디서 무너지는가(병목).

> 이번 테스트의 1차 목표는 명시적으로 **정합성**(오버셀 0)이었다. 성능은 병목 지점 규명이 목표.

## 2. 부하테스트 유형 (부하 프로파일별)

| 유형 | 부하 모양 | 무엇을 보나 | 이번 실측 |
|---|---|---|---|
| **Smoke** | 1 VU 1회 | 경로/토큰/시드 정상 동작 (측정 아님) | `smoke.js` |
| **Load (Steady)** | 목표 VU까지 ramp 후 **장시간 유지** | 정상 기대 부하에서 latency·오류율이 SLA 안인가 | `steady.js` 200 VU 5분 |
| **Stress** | 한계 넘을 때까지 **계속 증가** | 어디서 무너지고 어떻게 무너지나(graceful?) | (spike가 일부 대체) |
| **Spike** | **짧은 시간 급증** 후 급감 | 갑작스런 트래픽(티켓오픈)에 견디나, 회복하나 | `spike.js` 0→1000 VU 10s |
| **Soak/Endurance** | 중간 부하 **수시간~수일** | 메모리 누수, 커넥션 누수, 성능 저하 누적 | 미실행(후속) |
| **경쟁/동시성** | N개 요청 **거의 동시** 발사 | race condition, lock 정합성 | `oversell-race.js` 500 VU 동시 |

핵심 구분: **Steady = "평소에 괜찮은가"**, **Spike = "순간 폭증에 견디나"**, **Soak = "오래 돌려도 괜찮은가"**. 세 축이 다른 결함을 잡는다.

## 3. 핵심 개념

### VU (Virtual User)
가상 사용자 = 요청을 순차로 반복하는 동시 실행 단위(스레드). VU 하나는 요청→응답→다음요청 루프. **VU 수 ≠ 초당 요청 수**. 응답이 빠르면 VU 하나가 초당 여러 요청, 느리면 1개 미만.

> 이번: `ramping-vus`(steady/spike, 시간에 따라 VU 증감) vs `per-vu-iterations`(oversell, VU당 정확히 1회 → 거의 동시 발사).

### Throughput (처리량)
초당 완료 요청 수(req/s, RPS). 시스템의 실효 처리 능력.

> spike에서 1000 VU를 넣어도 throughput은 **~225 req/s로 수렴** = 풀 10과 락이 만든 상한. VU를 더 넣어도 이 값은 안 오르고 대기(latency)만 늘어난다. 이게 "포화점".

### Latency (지연) — 반드시 분포로 본다
평균(avg)은 거짓말을 한다. 꼬리(tail)가 사용자 경험을 지배. **퍼센타일**로 본다:

- **p50 (median)**: 절반이 이보다 빠름. "보통 경험".
- **p95**: 95%가 이 안. 나머지 5%는 이보다 느림.
- **p99**: 상위 1% 꼬리. 대량 트래픽이면 이 1%가 수천 명.
- **max**: 최악값. 타임아웃·이상치 탐지.

> 이번 steady: avg 1.28s인데 **max 43s**. 평균만 봤으면 43초 대기(+실패)를 놓쳤다. p95(2.46s)와 max 사이 간극 = 꼬리가 길다 = 큐잉 병목 신호.

### 왜 꼬리가 생기나 — Little's Law 직관
`동시처리중인_요청수 = throughput × 평균응답시간`. 처리 창구(여기선 풀 10)가 고정인데 유입이 늘면, 초과분은 **큐에서 대기**. 대기시간이 응답시간에 더해져 꼬리가 길어진다. 유입이 처리율을 넘으면 큐가 무한히 쌓여 결국 타임아웃.

## 4. 무슨 지표를 보나 (레이어별)

부하테스트는 **클라이언트 지표만 보면 절반만 아는 것**. 서버 내부를 함께 봐야 원인을 안다.

### 4.1 클라이언트 측 (k6)
| 지표 | 의미 |
|---|---|
| `http_req_duration` (p50/p95/p99/max) | 전체 왕복 지연 분포 |
| `http_req_waiting` (TTFB) | 서버 처리 시간(연결 제외) — 서버가 느린지 네트워크가 느린지 분리 |
| `http_req_failed` | 실패율. **0이 아니면 항상 원인 규명** |
| `http_reqs` rate | throughput(RPS) |
| custom counter (`ticketing_result`) | **비즈니스 결과** — HTTP 200이어도 SOLD_OUT/DUPLICATE/MAX일 수 있어 별도 기록 필수 |

> 함정: `POST /api/ticketing/requests`는 SOLD_OUT도 HTTP 200. status만 보면 "다 성공"으로 오독. 그래서 응답 바디의 `result`를 custom counter로 찍었다.

### 4.2 서버 자원 측 — 병목의 진짜 원인
| 지표 | 무엇을 잡나 |
|---|---|
| **Hikari `connections.active`** | 사용 중 DB 커넥션. **max에 붙으면 풀 포화** |
| **Hikari `connections.pending`** | 커넥션 대기 스레드 수. **>0이면 풀이 병목** |
| Postgres `pg_locks` / `pg_stat_activity` | 락 대기, 활성 커넥션 |
| Kafka consumer lag | 비동기 소비가 생산을 못 따라가는지 |
| CPU/MEM (`docker stats`) | 자원 고갈 여부 |

> 이번 병목 규명의 결정타: spike 중 Hikari `active=10(=max)` 고정 + `pending=189`. 클라이언트 p95 4.97s만으로는 "느리다"까지만 알지만, 이 두 값이 **"풀 10이 원인"**을 못박았다. → actuator로 Hikari 메트릭을 노출시킨 이유.

## 5. 방법론 — 어떻게 했나

### 5.1 절차
```
1. Smoke      → 경로/토큰/시드 정상 확인 (측정 전 사전점검)
2. 경쟁 테스트 → 즉시 DB 정합성 검증 → 재시딩
3. Steady     → 정상 부하 latency/오류율
4. Spike      → 급증 견디는지 + Hikari 풀 관찰
5. 결과 정리
```

### 5.2 부하 도구 — k6
- JS로 시나리오 작성, `ramping-vus`/`per-vu-iterations` executor로 부하 모양 표현.
- `thresholds`로 합격선 코드화(p95<X면 자동 FAIL).
- `SharedArray`로 토큰 로드, VU별 라운드로빈.

### 5.3 인증 우회
로그인 흐름을 타면 로그인 자체가 부하가 됨 → 순수 대상 API만 재려면 우회. `InternalApiJwtService`와 동일 규칙으로 internal JWT를 **사전 서명**(`issue-tokens.js`)해 backend가 신뢰하는 토큰을 직접 만듦.

### 5.4 정합성 검증은 DB로 (필수)
k6는 HTTP 응답만 본다. 오버셀 여부는 **DB를 직접 조회**해 판정(`verify-oversell.sh`: 실제 티켓 수 vs 초기 재고 vs remaining). 응답과 영속 상태가 일치하는지까지 확인해야 진짜 검증.

### 5.5 raw 데이터 보존
요약(p95)만 남기면 재분석 불가. 계획 §8: k6 `--out json`(요청 단위 NDJSON), DB before/after 스냅샷, 시스템 메트릭 CSV를 raw로 남긴다.

## 6. 함정 / 교훈 (이번에 실제로 겪음)

- **평균의 함정**: avg 1.28s 뒤에 max 43s. 항상 분포·꼬리를 봐라.
- **HTTP status ≠ 비즈니스 결과**: 200 안에 SOLD_OUT 섞임. custom metric 필수.
- **VU ≠ throughput**: 1000 VU 넣어도 처리량은 풀이 정한 ~225 RPS. 초과 VU는 대기로 전환.
- **클라이언트 지표만으론 원인 모름**: 서버 자원(Hikari pending)을 봐야 "왜"가 나온다.
- **부하 지속시간이 결함 종류를 바꾼다**: 같은 병목이 spike(30s)에선 실패 0, steady(5m)에선 타임아웃 실패. 큐가 쌓일 시간을 줘야 드러나는 결함이 있다.
- **테스트 전제가 코드와 맞는지 확인**: 계획의 "draft 낙관락 409" 전제가 실제 구현(단순 카운터)과 불일치 → 실측에서 발견해 계획 정정.

## 7. 병목 해소의 일반 순서 (참고)

1. **측정으로 병목 특정** (추측 금지) — 이번엔 Hikari 풀.
2. **가장 싼 레버부터**: 설정값(풀 크기) → 쿼리/락 설계(원자적 UPDATE) → 아키텍처(대기열/캐시/샤딩).
3. **하나씩 바꾸고 재측정** (A/B). 여러 개 동시에 바꾸면 무엇이 효과인지 모름.

> 이번 후속 1순위: 풀 10→20/30 A/B로 pending·p95 이동 관찰(가장 싼 레버).
