# PERFO 포트폴리오 데모 운영안

구현 단계로 바로 넘어가려면 [03_PORTFOLIO_DEMO_IMPLEMENTATION_SPEC.md](./03_PORTFOLIO_DEMO_IMPLEMENTATION_SPEC.md)를 참고한다.

## 1. 목적

이 문서는 `PERFO`를 포트폴리오 프로젝트로 소개할 때, 인사담당자나 면접관이 실제 서비스를 짧은 시간 안에 직접 체험할 수 있도록 데모 배포 전략과 운영 방식을 정리한 문서다.

핵심 목표는 다음과 같다.

- 가입 절차보다 서비스 체험을 먼저 보여준다.
- 공개 이벤트 조회, 예매, 예약 QR, 운영자 검표까지 핵심 플로우를 짧게 경험하게 한다.
- 지원 시점마다 데이터를 수동으로 정리하지 않아도 되도록 데모를 자동 복구 가능한 상태로 유지한다.
- 외부 공개 리스크를 통제하면서도 링크 하나로 쉽게 공유 가능하게 만든다.

## 2. 왜 기존 방식과 다르게 가야 하는가

이전 포트폴리오에서는 S3 기반 클라우드 스토리지 데모 특성상, "지원할 때마다 티켓을 발급하고 링크로 진입시켜 회원가입 후 사용"시키는 방식이 비교적 자연스러웠다.

하지만 `PERFO`는 성격이 다르다.

- 이 프로젝트의 강점은 인증 폼이 아니라 `공개 이벤트`, `예약`, `QR`, `검표`까지 이어지는 서비스 흐름이다.
- 인사담당자는 가입 UX보다 "이 서비스가 무엇을 해결하고 어떤 운영 흐름을 설계했는지"를 더 빨리 확인해야 한다.
- 공유 계정 한 개만 던지는 방식은 예약 수량, 사용 완료 상태, QR 토큰이 쉽게 꼬인다.

따라서 이번 프로젝트는 `회원가입 유도형 데모`보다 `체험 우선형 데모`가 더 적합하다.

## 3. 권장 데모 전략

권장안은 아래 3가지를 결합한 형태다.

1. `공개 진입`
2. `1클릭 데모 로그인`
3. `자동 초기화 가능한 데모 데이터`

즉, 사용자는 먼저 공개 이벤트를 보고 서비스 맥락을 이해한 뒤, 필요할 때만 데모 세션으로 진입해 보호된 화면을 체험하게 한다.

## 4. 추천 사용자 동선

### 4.1 기본 동선

데모 URL 예시:

- `https://demo.perfo.example.com`
- 또는 보호 링크 기반 `https://perfo-demo.vercel.app`

첫 화면에서는 아래 두 가지 경로만 선명하게 보여준다.

1. `관람객 체험`
2. `운영자 체험`

### 4.2 관람객 체험

관람객 체험은 아래 순서로 진행한다.

1. 공개 이벤트 목록 페이지 진입
2. 이벤트 상세 페이지 확인
3. `예매하기` 클릭
4. 비로그인 상태면 `데모 로그인` 또는 `일반 로그인` 선택
5. 데모 로그인 후 예매 완료
6. 예약 상세에서 QR 표시

보여주고 싶은 메시지는 분명하다.

- 이 프로젝트는 공개 프로모션/유입 페이지를 가질 수 있다.
- 로그인 이후 실제 예약/티켓 사용 플로우로 자연스럽게 이어진다.
- 예약 결과가 QR 기반 입장 경험으로 연결된다.

### 4.3 운영자 체험

운영자 체험은 아래 순서로 진행한다.

1. `운영자 체험` CTA 클릭
2. 데모 운영자 세션으로 즉시 로그인
3. `마이 티켓` 또는 `검표 스캔` 화면으로 이동
4. 예약 QR 토큰 검표
5. 성공/실패 상태가 화면에서 즉시 반영되는 것 확인

보여주고 싶은 메시지는 다음과 같다.

- 단순 예약 화면이 아니라 운영자 워크플로우까지 설계되어 있다.
- 발급 상태, 검표 상태, QR 검증 플로우가 연결되어 있다.
- 사용자용 화면과 운영자용 화면이 한 제품 안에서 이어진다.

## 5. 왜 회원가입을 기본 경로에서 빼야 하는가

회원가입은 기능 소개용으로는 의미가 있지만, 기본 진입 경로로는 마찰이 크다.

- 인사담당자는 실제 메일 인증이나 비밀번호 생성에 시간을 쓰고 싶어 하지 않는다.
- 데모마다 새 계정을 만들면 데이터가 누적되고 관리 비용이 생긴다.
- 동일 메일 재사용, 인증 코드 만료, 소셜 로그인 설정 문제는 체험 이탈 요소가 된다.

따라서 기본 경로는 다음처럼 정리한다.

- 기본 경로: 공개 이벤트 보기 -> 데모 로그인 -> 예매/QR/검표 체험
- 보조 경로: 필요 시 회원가입 화면도 접근 가능

## 6. 구현 원칙

### 6.1 체험 우선

첫 30초 안에 사용자가 실제 서비스 화면을 보게 해야 한다.

### 6.2 설명 최소화

긴 설명문보다 `지금 체험해보기` 버튼과 짧은 안내가 더 효과적이다.

### 6.3 실패 복구 가능

누가 먼저 예약했는지, 누가 이미 사용 처리했는지에 따라 데모가 망가지지 않도록 리셋 가능해야 한다.

### 6.4 링크 공유 단순화

지원서에 한 줄로 넣을 수 있어야 한다.

예시:

`데모: 공개 이벤트 조회 -> 예매 -> QR 확인 -> 운영자 검표까지 3분 내 체험 가능합니다.`

## 7. 현재 코드베이스 기준 활용 가능한 구조

현재 프론트엔드에는 포트폴리오 데모에 활용하기 좋은 흐름이 이미 있다.

- 공개 이벤트 진입 허용: [frontend/proxy.ts](../../frontend/proxy.ts)
- 공개 이벤트 목록: [frontend/app/[locale]/(main)/events/page.tsx](../../frontend/app/[locale]/(main)/events/page.tsx)
- 공개 이벤트 상세: [frontend/app/[locale]/(main)/events/[eventId]/page.tsx](../../frontend/app/[locale]/(main)/events/[eventId]/page.tsx)
- 예약 QR 페이지: [frontend/app/[locale]/(main)/reserved/[reservationId]/page.tsx](../../frontend/app/[locale]/(main)/reserved/[reservationId]/page.tsx)
- 검표 스캔 페이지: [frontend/app/[locale]/(scanner)/my-tickets/[ticketId]/scan/page.tsx](../../frontend/app/[locale]/(scanner)/my-tickets/[ticketId]/scan/page.tsx)

즉, 전체 플로우를 새로 만드는 것이 아니라, `데모 진입 UX`와 `데모 계정/데이터 운영`만 정리하면 된다.

## 8. 최종 권장안

가장 추천하는 방식은 아래와 같다.

### 8.1 진입 구조

- `/demo` 전용 랜딩 페이지 제공
- 랜딩에서 `관람객 체험` / `운영자 체험` 버튼 제공
- 공개 이벤트 페이지는 로그인 없이 접근 허용
- 보호된 화면은 데모 로그인 버튼으로 빠르게 진입

### 8.2 인증 구조

우선순위는 아래 순서다.

1. `1클릭 데모 로그인`
2. `고정 데모 계정`
3. `수동 회원가입`

가장 좋은 UX는 버튼 한 번으로 데모 세션을 부여하는 방식이다.

예시:

- `관람객 데모 시작`
- `운영자 데모 시작`

버튼을 누르면 서버가 미리 준비된 데모 사용자 세션을 발급하거나, 임시 계정을 생성하고 세션을 시작한다.

## 9. 데모 계정 전략 비교

### 9.1 옵션 A: 고정 데모 계정

예시:

- `demo-viewer@perfo.local`
- `demo-operator@perfo.local`

장점:

- 구현이 가장 빠르다.
- 로그인 버튼만 연결하면 바로 배포 가능하다.

단점:

- 동시 접속 시 같은 계정 데이터를 공유한다.
- 예약/검표 상태가 꼬일 수 있다.
- 비밀번호 노출형 데모는 다소 투박해 보인다.

적합한 경우:

- 빠르게 포트폴리오 링크를 완성해야 할 때
- 초기 버전 데모를 먼저 만들고 싶을 때

### 9.2 옵션 B: 역할별 자동 세션 발급

예시:

- `POST /api/demo/session`
- body: `{ "role": "viewer" | "operator" }`

서버 동작 예시:

1. 역할에 맞는 데모 사용자 선택
2. 세션/쿠키 발급
3. 추천 화면으로 리다이렉트

장점:

- 사용자는 비밀번호를 입력하지 않아도 된다.
- 체험 시작 속도가 빠르다.
- 지원서/포트폴리오에서 보여주기 좋다.

단점:

- 인증 우회용 데모 엔드포인트 설계가 필요하다.
- 운영 환경에서 접근 제어를 더 명확히 해야 한다.

적합한 경우:

- 포트폴리오 완성도를 높이고 싶을 때
- UX를 더 매끈하게 만들고 싶을 때

### 9.3 옵션 C: 방문마다 임시 데모 계정 생성

예시:

- `viewer-demo-20260515-abc123`
- `operator-demo-20260515-def456`

장점:

- 데이터 충돌을 크게 줄일 수 있다.
- 사용자마다 독립된 체험 공간을 만들기 쉽다.

단점:

- 구현과 정리 비용이 가장 높다.
- 계정/예약/티켓 정리 작업이 필요하다.

적합한 경우:

- 포트폴리오보다 실제 베타 데모에 가까운 운영을 원할 때

### 9.4 결론

포트폴리오 목적이라면 다음 순서를 추천한다.

1. 1차: `고정 데모 계정`으로 빠르게 오픈
2. 2차: `자동 데모 세션 발급`으로 개선

즉, 지금 당장 만드는 버전은 단순하게 가고, 시간이 허락하면 UX를 고도화하는 방향이 가장 현실적이다.

## 10. 데모 데이터 전략

데모는 기능보다 데이터가 더 중요하다. 아무리 화면이 좋아도, 예매 수량이 0이거나 QR이 이미 사용 처리되어 있으면 체험이 망가진다.

### 10.1 반드시 준비할 시드 데이터

최소한 아래 데이터는 고정 시드로 필요하다.

1. 공개 이벤트 1개
2. 링크 전용 이벤트 1개
3. 관람객 데모 유저 1개
4. 운영자 데모 유저 1개
5. 예매 가능한 재고가 남아 있는 이벤트 상태
6. 예약 완료 티켓 1개 이상
7. 검표 가능한 QR 토큰 테스트용 예약 상태
8. 이미 사용 완료된 티켓 1개

### 10.2 추천 시나리오 데이터

#### A. 공개 예매용 이벤트

- 이벤트명: `PERFO Showcase 2026`
- 상태: `OPEN`
- 재고: 충분히 남아 있음
- 목적: 이벤트 목록과 상세, 예매 진입 확인

#### B. 링크 전용 이벤트

- 이벤트명: `PERFO Private Invitation`
- 상태: `OPEN`
- 노출 방식: `LINK_ONLY`
- 목적: 공개/비공개 노출 모델을 설명하기 위함

#### C. 예약 완료 티켓

- 예약 상태: 성공
- QR 발급 가능
- 목적: 예약 상세와 QR 체험

#### D. 운영자 검표용 티켓

- 상태: `VERIFYING`
- 목적: 스캔 화면에서 성공/실패 결과 시연

#### E. 실패 케이스 데이터

- 이미 사용됨
- 잘못된 QR
- 재고 부족

이런 실패 케이스까지 준비해두면 면접 중 질문 대응이 쉬워진다.

## 11. 데이터 초기화 전략

데모는 반드시 리셋 전략이 있어야 한다.

### 11.1 최소 전략

- 매일 새벽 전체 시드 데이터 재적재
- 예약/검표/토큰 상태 초기화

### 11.2 권장 전략

- 배포 환경에 `demo reset` 스크립트 준비
- 스케줄러로 주기적 초기화
- 필요 시 수동 초기화 버튼 또는 관리자 전용 엔드포인트 제공

### 11.3 리셋 주기 권장안

- 기본: 하루 1회
- 지원서 제출 직후: 수동 1회
- 면접 직전: 수동 1회

즉, "항상 최신 상태"보다 "중요한 시점에 반드시 정상 상태"를 보장하는 쪽이 더 현실적이다.

## 12. `/demo` 랜딩 페이지 제안

### 12.1 목적

이 페이지는 기능 설명 페이지가 아니라, 사용자를 가장 짧은 경로로 핵심 체험에 진입시키는 페이지여야 한다.

### 12.2 화면 구성 제안

섹션 구성:

1. Hero
2. 체험 선택 카드 2개
3. 3분 체험 가이드
4. 선택 기능 소개
5. 기술 스택 / 구현 포인트

### 12.3 Hero 문구 예시

제목:

`PERFO Demo`

부제:

`공개 이벤트 조회부터 예약 QR, 운영자 검표까지 이어지는 프리미엄 티켓팅 플로우를 직접 체험해보세요.`

버튼:

- `관람객 체험 시작`
- `운영자 체험 시작`

### 12.4 관람객 카드 예시

제목:

`관람객 체험`

설명:

`공개 이벤트를 보고, 데모 계정으로 바로 예매한 뒤 예약 QR을 확인합니다.`

도착 지점:

- 비로그인: `/ko/events`
- 데모 로그인 후: `/ko/events/{demoEventId}`

### 12.5 운영자 카드 예시

제목:

`운영자 체험`

설명:

`발급된 티켓을 관리하고 QR 검표 결과를 확인하는 운영자 흐름을 체험합니다.`

도착 지점:

- 데모 로그인 후: `/ko/my-tickets/{ticketId}/scan`

### 12.6 3분 체험 가이드 예시

1. 공개 이벤트를 확인합니다.
2. 데모 로그인으로 예매 또는 운영자 체험을 시작합니다.
3. QR 확인 또는 검표까지 완료합니다.

### 12.7 주의 문구 예시

## 14. 배포 전략 제안

### 14.1 가장 현실적인 선택

프론트엔드가 Vercel 기반이라면 다음 조합이 가장 실용적이다.

- Vercel 배포
- 필요 시 Deployment Protection 적용
- 공유 대상에게 Shareable Link 전달

이 방식은 로그인형 앱 데모를 링크 단위로 통제하기 쉽다.

참고:

- Vercel Deployment Protection
- Vercel Shareable Links

### 14.2 AWS 스타일 접근 제어와의 비교

CloudFront signed URL은 개별 파일이나 보호 리소스 제공에는 적합하지만, 여러 화면 이동과 세션이 필요한 앱 데모에는 관리 복잡도가 커질 수 있다.

즉, 이번 프로젝트는 예전 S3 중심 데모처럼 `스토리지 링크 보호`보다 `앱 진입 보호 + 데모 계정 관리`가 더 중요하다.

## 15. 보안 주의사항

데모 환경은 편해야 하지만, 운영 환경 보안 기준을 무너뜨리면 안 된다.

반드시 지킬 원칙:

- 데모 전용 계정은 실제 사용자 데이터와 분리한다.
- 데모 계정 권한은 최소 권한만 부여한다.
- 데모 세션 발급 엔드포인트는 운영 환경에서 제한적으로만 노출한다.
- 데모용 시크릿과 운영용 시크릿을 분리한다.
- 외부 공개가 부담되면 배포 레벨 접근 보호를 적용한다.

추가 권장사항:

- 데모 환경은 production 본 데이터베이스를 절대 쓰지 않는다.
- 파일 업로드/푸시/외부 발송 기능은 비활성화하거나 샌드박스 환경으로 돌린다.
- 메일/알림 발송은 mock 또는 no-op 처리한다.

## 18. 최종 제안

이번 `PERFO`는 예전처럼 "지원할 때마다 개별 링크를 만들고 회원가입부터 시작시키는 데모"보다, 아래 구조로 가는 것이 더 좋다.

1. 공개 이벤트는 바로 보여준다.
2. 보호된 체험은 `데모 시작` 버튼으로 바로 들어가게 만든다.
3. 관람객 체험과 운영자 체험을 분리한다.
4. 데이터는 매일 또는 필요 시 자동 초기화한다.
5. 지원서에는 `3분 체험 가이드`를 함께 제공한다.

한 줄로 정리하면 다음과 같다.

`이번 포트폴리오 데모는 가입 유도형이 아니라 체험 우선형으로 설계하고, 공개 이벤트 -> 데모 세션 -> QR/검표까지 핵심 플로우를 가장 짧게 보여주는 방향이 적합하다.`
