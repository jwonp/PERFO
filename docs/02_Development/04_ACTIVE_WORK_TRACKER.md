# PERFO 현재 작업 정리

이 문서는 지금 진행 중인 작업들 중에서 서로 섞여 있거나, 문서만 있고 실행 단위가 분리되지 않은 것들을 다시 정리한 추적 문서다.

기준은 단순하다.

- 이미 방향이 정해진 것
- 아직 구현으로 안 내려간 것
- 바로 다음 액션이 필요한 것

## 1. 현재 가장 정리가 필요한 작업

지금 기준으로 가장 정리가 덜 된 축은 아래 4개다.

1. 포트폴리오 데모 작업
2. 데모 데이터/운영 자동화
3. 배포/공유 방식 결정
4. 브랜치와 작업 단위 관리

## 2. 작업 축별 현재 상태

### 2.1 포트폴리오 데모

관련 문서:

- [02_PORTFOLIO_DEMO_PLAN.md](./02_PORTFOLIO_DEMO_PLAN.md)
- [03_PORTFOLIO_DEMO_IMPLEMENTATION_SPEC.md](./03_PORTFOLIO_DEMO_IMPLEMENTATION_SPEC.md)

현재 상태:

- 데모 방향은 정리되어 있다.
- 구현 스펙도 정리되어 있다.
- 하지만 아직 코드 작업은 시작하지 않았다.

이미 정리된 것:

- 왜 회원가입 유도형보다 체험 우선형이 맞는지
- `/demo` 페이지가 필요하다는 점
- 관람객/운영자 시나리오를 분리해야 한다는 점
- 고정 데모 계정 2개로 MVP를 시작하는 것이 현실적이라는 점

아직 비어 있는 것:

- `/demo` 실제 페이지
- `/demo` public route 허용
- 데모 계정 빠른 입력 UX
- demo message 번역

지금 해야 할 다음 액션:

1. `/demo` 페이지 구현
2. `frontend/proxy.ts`에 `/demo` 공개 경로 추가
3. 로그인 페이지에 데모 계정 빠른 입력 UX 추가
4. 관련 테스트 추가

### 2.2 데모 데이터/운영 자동화

관련 문서:

- [03_PORTFOLIO_DEMO_IMPLEMENTATION_SPEC.md](./03_PORTFOLIO_DEMO_IMPLEMENTATION_SPEC.md)

현재 상태:

- 어떤 데이터가 필요한지는 정리됐다.
- 하지만 실제 재시드 방식은 아직 없다.

이미 정리된 것:

- 데모 관람객 계정 필요
- 데모 운영자 계정 필요
- 공개 이벤트 1개 필요
- 링크 전용 이벤트 1개 필요
- 예약 성공/사용 완료/검표 가능 데이터가 필요

아직 비어 있는 것:

- `scripts/reset-demo-data.sh`
- SQL 기반 초기화로 갈지, Kotlin 서비스로 갈지 결정
- demo mode 환경변수 실제 배치

지금 해야 할 다음 액션:

1. 데모 데이터 리셋 방식을 `스크립트 우선`으로 확정
2. 필요한 사용자/이벤트/티켓 시드 값을 표 형태로 확정
3. 반복 실행 가능한 reset 스크립트 작성

### 2.3 배포/공유 방식

현재 상태:

- 방향성은 있다.
- 하지만 실제로 어떤 링크를 이력서에 넣을지는 아직 안 정해졌다.

정리된 것:

- 완전 공개보다 보호 링크 기반 공유가 더 적합하다.
- demo 전용 배포가 production과 분리되는 편이 낫다.

아직 비어 있는 것:

- 최종 demo URL
- 접근 보호 방식
- 배포 환경 분리 수준

지금 해야 할 다음 액션:

1. `Vercel Shareable Link`로 갈지 결정
2. demo 전용 도메인/서브도메인 여부 결정
3. 지원서에 넣을 최종 문구 확정

### 2.4 브랜치와 작업 단위 관리

관련 문서:

- [01_RELEASE_VERSIONING.md](./01_RELEASE_VERSIONING.md)

현재 상태:

- 문서상 브랜치 정책은 정리되어 있다.
- 하지만 실제로 이번 작업은 아직 별도 feature branch로 나뉘지 않았다.

정리된 것:

- release 브랜치 규칙
- 버전 관리 규칙

아직 정리가 필요한 것:

- 포트폴리오 데모 구현 브랜치
- 문서 작업과 구현 작업의 분리 기준

지금 해야 할 다음 액션:

1. 구현 전에 `feat/portfolio-demo` 같은 브랜치 생성
2. 문서 작업과 코드 작업을 커밋 단위로 분리

## 3. 현재 기준 우선순위

지금 해야 하는 순서는 아래가 맞다.

### P0

- `/demo` 페이지 구현
- `/demo` 공개 라우트 허용
- 데모 로그인 UX 정리

### P1

- 데모 계정/이벤트/티켓 시드 확정
- reset 스크립트 작성
- demo 배포 URL 확정

### P2

- 자동 데모 세션 발급
- 관리자용 리셋 기능
- 데모 운영 헬스체크

## 4. 현재 작업을 한 문장으로 요약하면

지금 `PERFO`에서 가장 정리가 덜 된 부분은 "포트폴리오 데모를 만들기 위한 생각과 문서는 충분한데, 그걸 실제 구현과 운영 단위로 끊어 실행하는 단계가 아직 비어 있다"는 점이다.

## 5. 바로 실행할 작업 묶음

다음 작업 묶음으로 끊는 것이 가장 깔끔하다.

### Track A. Demo UI

- `/demo` 페이지
- demo components
- locale messages
- proxy 공개 경로

완료 기준:

- 비로그인 사용자가 `/ko/demo`로 들어가 체험 경로를 이해할 수 있다.

### Track B. Demo Auth UX

- 로그인 페이지 데모 계정 빠른 입력
- callbackUrl 유지

완료 기준:

- 관람객/운영자 데모 계정으로 빠르게 로그인할 수 있다.

### Track C. Demo Data Ops

- 데모 사용자/이벤트/티켓 시드
- reset 스크립트
- 운영 점검 체크리스트

완료 기준:

- 데모 데이터가 깨져도 반복적으로 정상 상태로 되돌릴 수 있다.

## 6. 추천 다음 작업

지금 가장 자연스러운 다음 작업은 아래 하나다.

`Track A. Demo UI`부터 구현으로 들어간다.

이유는 단순하다.

- 사용자에게 바로 보이는 결과가 나온다.
- 현재 문서화된 방향과 가장 직접적으로 연결된다.
- backend reset 스크립트보다 검증 비용이 낮다.

## 7. 정리 결과

현재 작업은 아래처럼 보면 된다.

- 끝난 것: 데모 방향/구현 스펙 문서화
- 안 끝난 것: `/demo` UI, 데모 로그인 UX, 시드/리셋 자동화
- 바로 해야 할 것: `feat/portfolio-demo` 브랜치에서 Demo UI부터 구현
