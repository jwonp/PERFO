## 1. 문서 목적

- 현재까지 구현된 내용을 MVP 오픈 기준으로 다시 정리한다.
- 이미 동작하는 범위와 아직 오픈하면 안 되는 범위를 구분한다.
- 남은 기능을 `P0`, `P1`, `P2` 우선순위로 나눠 개발 순서를 명확히 한다.
- 빠른 오픈을 위해 무엇을 이번 MVP 범위에서 제외할지 함께 결정할 수 있게 한다.

## 2. 현재 판단

현재 PERFO는 아래 수준까지는 구현이 진행된 상태다.

- 로그인 이후 메인 앱 구조
- 이벤트 탐색 화면
- 발급 티켓 관리 화면
- 예매 티켓 목록과 예약 상세 진입
- 티켓팅 요청 코어
- QR 검표 API와 스캐너 화면
- 알림/푸시/프로필 편집
- 티켓팅 outbox, projection, 관측성 기초

즉 서비스의 주요 축은 이미 보인다.

하지만 현재 상태를 그대로 운영 오픈하기에는 아래 문제가 남아 있다.

- 인증 범위가 중간 단계에 머물러 있다.
- 일반 사용자와 운영자 권한 분리가 없다.
- 이벤트 공개/판매 시점 계산이 운영 의도와 다를 가능성이 있다.
- 예매 결과 UX가 비즈니스 결과를 정확히 반영하지 않는다.
- QR 토큰 발급과 예약 조회 경계가 충분히 보호되지 않았다.

따라서 현재 상태는 "구조 검증과 내부 시연은 가능하지만, 대외 오픈 전에는 P0 정리가 필요한 상태"로 본다.

## 3. 현재 구현 현황

### 3.1 사용자 앱

이미 있는 것:

- 메인 탭 구조
  - `events`
  - `reserved`
  - `my-tickets`
  - `profile`
- 이벤트 목록: `frontend/app/[locale]/(main)/events/page.tsx`
- 이벤트 상세와 예매 버튼: `frontend/app/[locale]/(main)/events/[eventId]/page.tsx`
- 예약 티켓 목록: `frontend/app/[locale]/(main)/reserved/page.tsx`
- 예약 상세 QR 화면: `frontend/app/[locale]/(main)/reserved/[reservationId]/page.tsx`
- 프로필 편집, 테마, 푸시 설정: `frontend/app/[locale]/(main)/profile/page.tsx`

현재 부족한 점:

- 이벤트 상세에서 수량 선택이 없다.
- 예매 실패 결과를 상태별로 나눠 보여주지 않는다.
- 예약 상세는 실제 QR 렌더링 대신 토큰 문자열만 표시한다.
- 일반 사용자에게도 운영자용 `my-tickets` 탭이 그대로 노출된다.

### 3.2 운영자 티켓 관리

이미 있는 것:

- 티켓 생성/수정
- 장소 자동완성
- 오픈 시각 입력
- 중복 구매 허용
- discovery mode 설정
- 이미지 업로드
- 예매 URL 복사/공유
- 스캔 화면 진입

현재 부족한 점:

- 운영자 전용 권한 모델이 없다.
- 운영자/일반 사용자 UI가 완전히 분리되지 않았다.
- 발급 티켓 상태와 실제 공개 판매 상태가 운영 의도와 다를 수 있다.

### 3.3 인증

이미 있는 것:

- NextAuth 기반 소셜 로그인 구조
- Google / Naver / Line provider
- 백엔드 OAuth 사용자 동기화
- 백엔드 일반 `signup/login` API
- 로그인/회원가입/인증/비밀번호 재설정 화면 UI

현재 부족한 점:

- 이메일/비밀번호 로그인 화면이 실제 인증을 수행하지 않는다.
- 회원가입 화면이 실제 `signup` API를 호출하지 않는다.
- 이메일 인증 코드 검증 로직이 없다.
- 비밀번호 재설정 API와 UI 연결이 없다.
- 계정/권한 모델이 운영자 분리를 반영하지 않는다.

정리:

- 이번 MVP를 빠르게 열려면 인증 범위를 "소셜 로그인 우선"으로 축소하는 안이 가장 현실적이다.

### 3.4 백엔드 코어

이미 있는 것:

- 인증 API
- 이벤트 공개 조회 API
- 티켓 생성/수정/이미지 API
- 티켓팅 요청 API
- 예약 목록 API
- QR 토큰 발급 API
- QR 검표 API
- 상태 전환 API
- outbox relay / projection / observability

현재 부족한 점:

- 역할 기반 권한 통제가 없다.
- 관리자/일반 사용자 경계가 API 수준에서 분리되지 않았다.
- 일부 공개 허용 엔드포인트가 MVP 보안 기준에 비해 넓다.
- 인증 실패/도메인 실패 케이스에 대한 운영용 에러 정책이 아직 단단하지 않다.

## 4. MVP 오픈 차단 이슈

### 4.1 P0-1. 인증 범위를 정리하지 않으면 사용자 진입이 혼란스럽다

현재 화면은 아래 모두를 보여준다.

- 이메일 진입
- 소셜 로그인
- 회원가입
- 인증 코드 입력
- 비밀번호 재설정

하지만 실제 완성된 것은 소셜 로그인 축에 더 가깝다.

따라서 선택지가 필요하다.

권장안:

- 이번 MVP는 `소셜 로그인 전용`으로 제한한다.
- 이메일/비밀번호 회원가입, 인증, 재설정 화면은 숨기거나 "준비 중"으로 내린다.
- 백엔드의 `signup/login` API는 내부 검증 또는 후속 단계로 남긴다.

대안:

- 이메일 기반 가입/로그인/인증/재설정 전 과정을 이번 MVP 안에 완성한다.
- 하지만 일정과 QA 범위가 커진다.

### 4.2 P0-2. 운영자와 일반 사용자의 권한을 분리해야 한다

현재는 로그인만 하면 다음 기능에 닿을 수 있다.

- `my-tickets` 탭
- 티켓 생성
- 티켓 수정
- 스캔 화면 진입

MVP 공개 서비스 기준으로는 아래가 필요하다.

- `USER`
- `ORGANIZER` 또는 `ADMIN`

최소 기준:

- 일반 사용자는 `events`, `reserved`, `profile`만 본다.
- 운영자만 `my-tickets`와 발급/수정/스캔 기능을 본다.
- 백엔드도 `/api/tickets/**`와 운영성 내부 기능을 role로 제한한다.

### 4.3 P0-3. 이벤트 공개 상태와 판매 시점 계산을 다시 맞춰야 한다

현재 발급 티켓에서 이벤트를 동기화할 때 다음 리스크가 있다.

- 판매 오픈 시각이 현재 시각으로 저장될 수 있다.
- `INACTIVE` 상태여도 공개 이벤트처럼 보일 수 있다.
- 운영자가 의도한 "오픈 전", "비공개", "비활성" 상태가 사용자에게 정확히 반영되지 않을 수 있다.

MVP 기준 고정 규칙이 먼저 필요하다.

- `INACTIVE`: 목록 비노출, 상세 접근 제한 또는 비활성 안내
- `ISSUING`: 오픈 전, 예매 불가
- `VERIFYING`: 판매 중
- `EXPIRED`: 종료

그리고 판매 시점은 아래처럼 단순화하는 것이 안전하다.

- `saleOpenAt = issuedTicket.openAt`
- `saleCloseAt = validDate 종료 시각`

### 4.4 P0-4. 예매 결과 UX를 도메인 결과 기반으로 고쳐야 한다

현재 상세 화면은 예매 요청이 HTTP 200만 반환되면 `reserved`로 이동한다.

하지만 티켓팅 코어는 본문 `result`로 아래를 구분한다.

- `SUCCESS`
- `NOT_OPEN`
- `SALE_CLOSED`
- `SOLD_OUT`
- `DUPLICATE_PURCHASE`
- `MAX_PER_USER_EXCEEDED`

프런트는 이 결과를 직접 해석해야 한다.

필수 수정:

- `SUCCESS`만 이동
- 실패 결과는 페이지에서 메시지로 표시
- 수량 선택 UI 추가
- 버튼 중복 제출 방지 유지

### 4.5 P0-5. QR/예약 경계 보안을 다시 잡아야 한다

현재 예약과 검표 흐름은 동작하지만 오픈 기준으로는 아래 정리가 필요하다.

- 예약 목록 조회는 본인 세션 기준으로만 접근
- QR 토큰 발급도 본인 예약 또는 허용된 운영자만 접근
- 검표 API는 공개 유지 여부를 의도적으로 결정
- 예약 상세는 실제 QR 시각화로 마무리

MVP 권장안:

- 예약 목록/예약 QR 발급은 세션 기반 보호
- 검표 API는 QR 서명 검증을 유지하되, 스캐너 진입은 운영자 권한만 허용

## 8. 실제 작업 진행 방식

이 문서는 단순 점검 문서가 아니라 실제 구현 순서를 통제하는 기준 문서로 사용한다.

작업 방식은 아래 원칙을 따른다.

- `P0`만 먼저 처리한다.
- 한 번에 큰 범위를 수정하지 않고 사용자 플로우 단위로 나눈다.
- 각 작업 묶음은 `구현 -> 테스트 -> 문서 반영`까지 한 번에 닫는다.
- 범위가 흔들리는 항목은 코드를 고치기 전에 먼저 정책을 고정한다.
- 공개 오픈 전까지는 신규 확장 기능보다 오픈 차단 이슈 제거를 우선한다.

실행 순서는 아래와 같다.

- 범위 확정
- 권한 분리
- 이벤트/예매 흐름 수정
- QR/예약 보안 정리
- 오픈 리허설

### 8.1 1차 작업. MVP 범위 고정

진행 상태:

- [x] 완료 (2026-05-09, 범위 재고정)

목표:

- 이번 MVP의 인증 범위를 명확히 고정한다.

권장 결정:

- 이번 MVP는 `소셜 로그인 + 이메일(credentials) 인증`을 함께 운영한다.

작업 내용:

- [x] 이메일 회원가입 UI 복원 및 실제 회원가입 완료까지 연결
- [x] 이메일/비밀번호 로그인 흐름 복원 및 NextAuth 세션 연결
- [x] 인증 코드 입력 화면을 실제 검증 흐름과 연결
- [x] 비밀번호 재설정 화면을 실제 재설정 API와 연결
- [x] 로그인 진입 문구와 라우팅을 이메일/소셜 병행 기준으로 정리

구현 메모:

- 로그인 화면에서 이메일 입력 후 `check-email` 결과에 따라 `login/password` 또는 `signup`으로 분기한다.
- 로그인 화면은 이메일 확인 분기와 소셜 로그인 진입만 유지하고, 별도 회원가입 CTA는 두지 않는다.
- `CredentialsProvider`를 추가해 백엔드 `login` API와 NextAuth 세션을 연결했다.
- 인증코드 요청/검증, 검증 완료 회원가입, 비밀번호 재설정 API를 추가했다.
- `MailSender` 인터페이스와 `ResendMailSender`를 추가해 인증 코드를 실제 메일 발송 경로에 연결했다.
- 인증코드 화면은 6자리 숫자 입력, 붙여넣기, 미완성 코드 방지, 누락된 이메일/회원가입 초안 방지 기준으로 UX를 보정했다.
- 현재 `app.auth.preview-code-enabled` 기본값은 켜져 있으므로 QA 환경에서는 preview code를 함께 확인할 수 있다. 운영에서는 비활성 전환이 필요하다.

완료 조건:

- 사용자는 이메일/소셜 중 실제 동작하는 인증 플로우로 진입할 수 있다.
- 회원가입, 로그인, 인증코드, 비밀번호 재설정이 하나의 흐름으로 연결된다.

주요 영향 범위:

- `frontend/app/[locale]/(auth)`
- `frontend/proxy.ts`
- `frontend/messages/*.json`

## 9. 테스트 및 검증 기준

### 8.1 기능 스모크

- 일반 사용자 로그인 후 `events`, `reserved`, `profile`만 노출
- 운영자 로그인 후 `my-tickets` 노출
- 운영자 이벤트 생성 후 목록/상세 반영
- 오픈 전 예매 시 `NOT_OPEN`
- 판매 중 예매 시 `SUCCESS`
- 매진 후 예매 시 `SOLD_OUT`
- 예약 QR 발급 성공
- 검표 1회 성공 후 2회차 `ALREADY_USED`

### 8.2 보안 스모크

- 비운영자는 티켓 생성/수정 불가
- 다른 사용자의 예약 조회 불가
- 다른 사용자의 QR 발급 불가
- 비로그인 사용자는 보호 경로 진입 불가

### 8.3 운영 스모크

- 내부 JWT 설정 확인
- DB migration 적용 확인
- 이미지 업로드/조회 확인
- 알림 브리지 동작 확인
- outbox / projection 메트릭 노출 확인

## 10. 문서 기준 결론

현재 PERFO는 MVP의 기반 구조는 충분히 구현되어 있다.

다만 대외 오픈 기준으로는 아래 다섯 가지를 먼저 해결해야 한다.

1. 인증 범위 확정
2. 운영자와 일반 사용자 권한 분리
3. 이벤트 공개/판매 상태 규칙 수정
4. 예매 결과 UX 수정
5. QR/예약 보안 경계 정리

가장 빠른 오픈 전략은 아래다.

- 인증은 소셜 로그인 우선
- 이메일 가입/인증/재설정은 후속
- 운영자 기능은 role 기반으로 분리
- 예매와 QR 흐름만 단단하게 완성

이 문서는 이후 실제 구현 작업의 기준 문서로 사용한다.
