# 웹과 HTTP 기초

백엔드는 결국 HTTP 요청을 받고 응답을 반환하는 시스템이다. Spring 문법보다 HTTP를 먼저 이해해야 한다.

## 왜 중요한가

컨트롤러를 작성할 수 있어도 HTTP를 이해하지 못하면 잘못된 메서드, 어색한 상태코드, 모호한 API를 계속 만들게 된다. 프레임워크는 도구이고, HTTP는 계약이다.

## 1. HTTP 기본

- Request / Response
- Method: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`
- Header, Body, Query Parameter, Path Variable
- 상태코드: `200`, `201`, `204`, `400`, `401`, `403`, `404`, `409`, `500`

### 어떻게 구분하는가

- Path Variable: 특정 자원을 식별할 때 사용
- Query Parameter: 검색 조건, 정렬, 페이지네이션처럼 부가 조건에 사용
- Header: 인증 정보, 콘텐츠 타입, 캐시 정책 같은 메타데이터
- Body: 생성/수정에 필요한 실제 데이터

## 2. REST 기본 감각

REST는 규칙집이라기보다 자원 중심 설계에 가깝다.

- URI는 자원을 표현한다.
- 동사는 HTTP Method가 맡는다.
- 응답 구조는 일관성이 있어야 한다.

### 예시

- `GET /api/users/1`
- `POST /api/auth/signup`
- `PATCH /api/tickets/10`

### 어떻게 설계하는가

- URI에는 행위를 넣기보다 자원을 넣는다.
- 행위가 애매하면 "이 요청이 자원을 조회하는가, 생성하는가, 수정하는가, 삭제하는가"로 다시 본다.
- 응답은 클라이언트가 다음 행동을 판단할 수 있게 일관되게 준다.

## 3. JSON

- 객체와 배열 구조 이해
- 직렬화 / 역직렬화 개념
- 요청 필드 누락, 타입 불일치 시 어떻게 되는지 이해

### 어떻게 점검하는가

- 요청 예시 JSON을 직접 써본다.
- 필드가 누락되면 validation으로 막을지, nullable로 받을지 먼저 정한다.
- 응답 JSON에서 내부 구현 세부사항이 노출되지 않는지 확인한다.

## 4. 인증과 인가 기초

- 인증: 누구인지 확인
- 인가: 무엇을 할 수 있는지 확인
- 세션과 토큰의 차이
- 쿠키와 헤더 기반 인증

### 어떻게 구분해서 생각하는가

- 인증은 "로그인 되었는가"
- 인가는 "이 리소스에 접근할 권한이 있는가"
- 둘이 섞이면 `401`과 `403`이 혼란스러워진다

## 5. 브라우저 관점에서 알아야 할 것

- CORS
- 쿠키 전송 조건
- same-origin
- 캐시 기초

### 어떻게 확인하는가

- 브라우저 개발자도구에서 요청 헤더와 응답 헤더를 본다.
- CORS 에러가 나면 서버 응답 헤더와 프론트 요청 origin을 같이 본다.
- 쿠키 기반 인증이면 `SameSite`, `Secure`, `HttpOnly` 설정을 체크한다.

## 6. API 설계에서 자주 놓치는 것

- 성공 응답만 설계하고 실패 응답은 비워두는 경우
- validation 실패와 비즈니스 실패를 구분하지 않는 경우
- 너무 많은 책임을 하나의 API에 넣는 경우

## 지금 당장 해볼 것

1. 현재 프로젝트 API 하나를 골라 요청/응답 구조를 문장으로 설명해본다.
2. `400`, `401`, `403`, `404`, `409`를 어떤 상황에 쓸지 직접 예시를 적어본다.
3. 브라우저 개발자도구나 Postman으로 실제 요청 헤더와 바디를 확인한다.

## 체크리스트

- HTTP 메서드와 상태코드를 의도에 맞게 고를 수 있다.
- Path Variable과 Query Parameter를 구분할 수 있다.
- 인증과 인가 차이를 설명할 수 있다.
- CORS 문제가 왜 발생하는지 안다.
- API 실패 응답도 설계해야 한다는 감각이 있다.
