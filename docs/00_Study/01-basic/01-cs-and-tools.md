# 개발 기본기와 CS

코프링을 배우기 전에 이 영역이 약하면 나중에 코드만 따라 치게 된다. 먼저 "왜 이렇게 동작하는지"를 설명할 수 있어야 한다.

## 왜 중요한가

Spring 코드를 잘 짜는 사람도, 장애가 났을 때 포트 충돌이나 환경변수 문제를 못 보면 실무에서 막힌다. 이 문서는 백엔드 프레임워크 바깥에서 돌아가는 기본 원리를 이해하기 위한 출발점이다.

## 1. 운영체제와 개발 환경

### 알아야 하는 것

- 프로세스와 스레드 차이
- 메모리 구조: stack, heap
- 파일 시스템과 경로
- 환경변수와 설정 파일
- 포트, PID, 프로세스 종료

### 실무 포인트

- 서버가 왜 안 뜨는지 볼 때 포트 충돌을 확인할 수 있어야 한다.
- 로그 파일, 환경변수, 실행 프로세스를 직접 볼 수 있어야 한다.
- 로컬 / dev / prod 환경 차이를 이해해야 한다.

### 익숙해져야 하는 명령어

- `pwd`, `ls`, `cd`
- `cat`, `less`, `tail -f`
- `grep`, `rg`, `find`
- `ps`, `lsof`, `kill`
- `env`

### 어떻게 익히면 되는가

- 서버가 안 뜰 때 먼저 `lsof -i :포트번호`로 포트 점유 여부를 본다.
- 로그를 볼 때는 파일 전체를 열기보다 `tail -f`로 최근 로그를 추적한다.
- 원하는 문자열을 찾을 때는 `grep`보다 `rg`를 우선 쓴다.
- "이 설정값이 어디서 들어왔지?"가 궁금하면 환경변수와 설정 파일을 같이 본다.

## 2. 네트워크 기초

### 알아야 하는 것

- IP, Port, DNS
- TCP와 UDP 차이
- 3-way handshake를 아주 간단히 설명할 수 있는 수준
- 요청과 응답의 흐름
- 프록시, 로드밸런서 개념

### 최소 설명 가능해야 하는 질문

- 브라우저에서 URL 입력 후 무슨 일이 일어나는가
- `localhost`와 `127.0.0.1`은 무엇인가
- 왜 백엔드 서버는 포트를 열어야 하는가

### 어떻게 공부하면 되는가

- 이론만 외우지 말고 브라우저 개발자도구 `Network` 탭을 켜고 실제 요청과 응답을 본다.
- 프론트와 백엔드를 각각 띄운 뒤, 포트가 다르면 왜 CORS가 걸리는지 직접 확인한다.
- 같은 API를 브라우저, Postman, curl로 각각 호출해보면 HTTP 감각이 빨리 붙는다.

## 3. 자료구조와 알고리즘 기초

백엔드 실무에서 코딩테스트만큼 깊게 쓰지는 않아도, 아래는 기본이다.

- 배열, 리스트, 맵, 셋 차이
- 시간복잡도 감각: `O(1)`, `O(n)`, `O(log n)`
- 정렬, 탐색 개념
- 스택, 큐의 쓰임

실무에서는 "이 데이터 구조를 왜 골랐는가"를 설명할 수 있으면 충분히 강하다.

### 어떻게 적용하는가

- 중복 제거가 목적이면 `List`보다 `Set`을 먼저 떠올린다.
- 키로 빠르게 찾는 구조면 `Map`을 먼저 생각한다.
- 순서가 중요한지, 중복 허용이 필요한지부터 정리하고 자료구조를 고른다.

## 4. 데이터베이스 기초

### 알아야 하는 것

- 테이블, 컬럼, 로우
- PK, FK
- 인덱스 기본 개념
- 정규화 기초
- `JOIN`이 왜 필요한가
- 트랜잭션의 목적

### 최소 SQL

- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`
- `JOIN`
- `GROUP BY`
- `ORDER BY`

### 어떻게 공부하면 되는가

- ORM부터 붙잡지 말고 SQL로 먼저 같은 결과를 직접 만들어본다.
- `users`, `tickets`, `reservations`처럼 실제 프로젝트 도메인을 떠올리며 테이블을 그려본다.
- 한 번에 복잡한 쿼리를 짜기보다, `SELECT` 후 조건 추가, `JOIN` 추가 식으로 단계적으로 만든다.

## 5. Git

### 꼭 알아야 하는 것

- working tree / staging area / commit
- branch
- merge 와 rebase 차이
- 충돌 해결
- `git status`, `git diff`, `git log`

### 실무 포인트

- 커밋은 작게 자른다.
- 의미 있는 커밋 메시지를 쓴다.
- 충돌 났을 때 무작정 덮어쓰지 않는다.

### 어떻게 해야 하는가

- 작업 시작 전 `git status`로 현재 상태를 본다.
- 커밋 전 `git diff`로 진짜 내가 의도한 변경인지 확인한다.
- 충돌이 나면 양쪽 코드를 다 읽고 "어떤 의도를 살려야 하는가"부터 판단한다.

## 6. 개발자로서의 사고방식

- 기능 구현 전 입력 / 출력 / 예외 / 실패 케이스를 먼저 본다.
- "돌아간다"와 "유지보수 가능하다"를 구분한다.
- 디버깅은 감이 아니라 재현과 로그로 한다.

## 지금 당장 해볼 것

1. 로컬에서 백엔드 프로세스를 띄우고 포트, 로그, 환경변수를 직접 확인한다.
2. 간단한 SQL을 직접 작성해 테이블 데이터를 조회해본다.
3. `git diff`와 `git log --oneline` 사용을 습관화한다.
4. 브라우저 개발자도구에서 실제 HTTP 요청과 응답을 본다.

## 체크리스트

- 프로세스와 스레드 차이를 설명할 수 있다.
- 포트 충돌을 직접 확인하고 해결할 수 있다.
- 기본 SQL을 직접 작성할 수 있다.
- Git 브랜치 작업과 충돌 해결을 할 수 있다.
- 로그를 보고 장애 원인을 좁혀갈 수 있다.
