# Kotlin 기초

코프링에서는 "자바를 코틀린 문법으로 옮기는 수준"을 넘어서야 한다. Kotlin다운 코드를 쓰는 것이 중요하다.

## 왜 중요한가

코틀린을 제대로 못 쓰면, 코드가 장황해지고 null 관련 버그가 늘어나고 DTO와 엔티티 경계도 흐려진다. 실무에서는 "문법을 안다"보다 "타입으로 의도를 드러내는가"가 더 중요하다.

## 먼저 알아둘 용어

- `val`: 한 번 할당한 뒤 다시 다른 값을 넣지 않는 읽기 전용 변수다. 자바의 `final` 변수에 가깝다.
- `var`: 값을 다시 바꿀 수 있는 변수다. 상태 변경이 필요한 경우에만 제한적으로 쓴다.
- `data class`: 데이터를 담기 위한 클래스로, `equals`, `hashCode`, `toString`, `copy` 등을 자동으로 만들어준다.
- nullable 타입: 값이 `null`일 수 있음을 타입에서 표현한 것이다. `String?`처럼 쓴다.
- non-null 타입: `null`이 들어오면 안 되는 타입이다. `String`처럼 `?`가 없다.
- scope function: 객체를 더 간결하게 다루기 위해 쓰는 함수 묶음이다. `let`, `run`, `apply`, `also`, `with`가 여기에 속한다.
- DTO: Data Transfer Object의 약자다. 계층 간 또는 API 요청/응답에 데이터를 전달하기 위한 객체다.
- Entity: DB 테이블과 매핑되는 객체다. JPA가 관리하며 생명주기와 영속성 상태를 가진다.

## 1. 문법 기초

- `val` 과 `var`
- 함수 선언
- 클래스, data class
- `if`, `when`, `for`
- 컬렉션 기초
- 문자열 템플릿

### 어떻게 익히면 되는가

- 새로 작성하는 변수는 기본적으로 `val`로 시작하고, 꼭 필요한 경우만 `var`로 바꾼다.
- if/else 블록을 값으로 반환하는 습관을 들인다.
- 단순 데이터 전달 모델은 `data class`를 우선 사용한다.

### 용어 설명

- 문자열 템플릿: `"name=$name"`처럼 문자열 안에 변수를 바로 넣는 문법이다.
- primary constructor: 클래스 이름 옆에서 바로 선언하는 기본 생성자다.
- 컬렉션: 여러 데이터를 모아 담는 구조다. 대표적으로 `List`, `Set`, `Map`이 있다.

## 2. null-safety

이건 코틀린의 핵심이다.

- nullable 타입: `String?`
- safe call: `?.`
- Elvis operator: `?:`
- non-null assertion: `!!`

### 용어 설명

- safe call `?.`: 왼쪽 값이 null이면 뒤 코드를 실행하지 않고 null을 반환한다.
- Elvis operator `?:`: 왼쪽 값이 null일 때 기본값을 주는 연산자다.
- non-null assertion `!!`: "절대 null이 아니다"라고 강제로 단정하는 문법이다. 틀리면 런타임 예외가 난다.

### 실무 포인트

- `!!`는 가능한 한 피한다.
- DTO, 엔티티, 응답 모델에서 null 허용 범위를 의식적으로 설계한다.
- optional한 값인지, 비즈니스상 필수 값인지 타입에서 드러나야 한다.

### 어떻게 적용하는가

- 요청값이 반드시 있어야 하면 타입을 nullable로 두지 않는다.
- nullable 값을 다뤄야 하면 `if (x == null)` 혹은 `?:`로 분기 의도를 명확히 적는다.
- `!!`가 보이면 "여기서 null이 절대 안 된다는 보장이 코드에 있는가"를 먼저 의심한다.

### 예시

```kotlin
fun nicknameOrDefault(nickname: String?): String {
    return nickname?.trim()?.takeIf { it.isNotEmpty() } ?: "anonymous"
}
```

위 코드는 "값이 없거나 비어 있으면 기본값을 쓴다"는 의도를 타입과 로직으로 같이 보여준다.

## 3. 객체지향과 Kotlin다운 표현

- primary constructor
- `init`
- `companion object`
- 확장 함수
- sealed class
- enum class
- 상속보다 조합 우선

### 용어 설명

- `init`: 객체 생성 직후 실행되는 초기화 블록이다.
- `companion object`: 클래스에 속한 정적 성격의 함수/값을 둘 수 있는 공간이다.
- 확장 함수: 기존 클래스를 수정하지 않고도 새 함수를 붙인 것처럼 쓰는 문법이다.
- `enum class`: 정해진 상수 집합을 표현하는 타입이다. 예: `ADMIN`, `USER`
- `sealed class`: 상속 가능한 하위 타입 집합을 제한하는 타입이다. 결과 유형이 닫혀 있을 때 유용하다.
- 조합: 상속 대신 필요한 객체를 내부 필드로 가지고 협력하게 만드는 방식이다.

### 어떻게 선택하는가

- 상태가 고정된 종류를 표현할 때는 `enum class`
- 성공 / 실패 / 로딩처럼 닫힌 결과 집합을 표현할 때는 `sealed class`
- 객체 생성 규칙이 있으면 `companion object`나 팩토리 함수를 고려
- 여러 곳에서 반복되는 유틸성 동작은 확장 함수로 빼되, 도메인 의미가 있어야 한다

## 4. 컬렉션과 함수형 스타일

- `map`, `filter`, `associate`
- `let`, `run`, `apply`, `also`, `with`

### 용어 설명

- `map`: 각 원소를 다른 형태로 변환한다.
- `filter`: 조건에 맞는 원소만 남긴다.
- `associate`: 컬렉션을 key-value 형태의 `Map`으로 바꾼다.
- `let`: null 체크 후 안전하게 이어서 작업할 때 자주 쓴다.
- `apply`: 객체를 초기화하고 자기 자신을 반환할 때 자주 쓴다.
- `also`: 부수효과 로그나 디버깅을 넣고 원래 객체를 그대로 넘길 때 쓴다.

### 실무 포인트

- scope function은 멋있게 쓰는 게 목적이 아니다.
- 읽기 어려워지면 평범한 코드가 낫다.

### 어떻게 해야 하는가

- 입력을 변환하는 흐름이면 `map`, 조건으로 거르면 `filter`를 먼저 생각한다.
- 한 줄로 줄이기보다 읽는 사람이 흐름을 따라가기 쉬운지가 우선이다.
- `let`, `apply`, `also`를 섞기 시작했는데 의미가 헷갈리면 일반 코드로 되돌린다.

## 5. 예외 처리

- `try-catch-finally`
- checked exception이 Kotlin에서 어떻게 보이는지
- 비즈니스 예외와 시스템 예외 분리

### 용어 설명

- checked exception: 자바에서 컴파일 시점에 처리 여부를 강제하는 예외다. Kotlin은 이를 강제하지 않는다.
- 비즈니스 예외: 규칙 위반 때문에 의도적으로 발생시키는 예외다. 예: 중복 이메일 가입
- 시스템 예외: DB 장애, 네트워크 장애처럼 시스템 자체 문제에서 생기는 예외다.

### 실무 포인트

- 예외 메시지는 디버깅 가능한 정보여야 한다.
- 예외를 무시하지 않는다.
- 어디서 잡고 어디서 던질지 레이어 기준이 있어야 한다.

### 어떻게 나누는가

- 컨트롤러: 예외를 직접 처리하기보다 적절한 응답으로 변환되게 맡긴다.
- 서비스: 비즈니스 규칙 위반 시 명시적인 예외를 던진다.
- 인프라 계층: 외부 시스템 예외를 서비스가 이해할 수 있는 형태로 감싼다.

### 예시 질문

- 회원가입 중 이메일 중복이면 어떤 예외를 던질 것인가
- DB 연결 실패는 사용자에게 어떤 응답으로 보낼 것인가

## 6. 데이터 모델링 감각

- DTO와 Entity를 분리한다.
- 요청 DTO와 응답 DTO를 분리한다.
- 엔티티를 그대로 API 응답으로 내보내지 않는다.

### 용어 설명

- 요청 DTO: 클라이언트가 서버에 보내는 입력 구조다.
- 응답 DTO: 서버가 클라이언트에 반환하는 출력 구조다.
- API 계약: 프론트와 백엔드가 주고받는 데이터 형식과 규칙이다.

### 왜 분리해야 하는가

- 엔티티는 DB 구조와 생명주기를 담고 있다.
- DTO는 API 계약을 표현한다.
- 둘을 섞으면 DB 구조 변경이 API 변경으로 번지기 쉽다.

### 어떻게 적용하는가

- `SignUpRequest`, `SignUpResponse`, `User`처럼 역할이 이름에서 드러나게 분리한다.
- 변환 책임은 controller나 dedicated mapper에서 관리하고, service 내부에 무분별하게 흩어지지 않게 한다.

## 7. 꼭 익혀야 하는 Kotlin 실무 습관

- 불변 객체를 우선 사용한다.
- nullable 최소화
- 함수는 짧고 목적이 분명하게 유지한다.
- 이름으로 의도를 드러낸다.

## 지금 당장 해볼 것

1. 현재 프로젝트에서 `!!` 사용 위치를 찾아 왜 필요한지 검토한다.
2. DTO와 엔티티가 섞인 부분이 있으면 역할을 구분해본다.
3. `var`를 `val`로 바꿔도 되는 코드를 찾아본다.
4. 복잡한 null 처리 코드를 Elvis operator나 early return으로 정리해본다.

## 체크리스트

- `val` 중심으로 코드를 작성할 수 있다.
- null-safety를 이해하고 `!!`를 남발하지 않는다.
- DTO, Entity, domain 역할을 구분할 수 있다.
- 컬렉션 변환 함수를 무리 없이 쓸 수 있다.
- Kotlin다운 코드와 억지 함수형 코드를 구분할 수 있다.
