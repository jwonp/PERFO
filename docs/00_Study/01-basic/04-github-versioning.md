# GitHub 버저닝과 릴리스 기본

GitHub에서 버저닝은 코드 변경 이력을 버전 단위로 관리하고, 어떤 시점의 배포본이 무엇인지 명확하게 남기는 작업이다. 실무에서는 보통 `git tag`, `GitHub Release`, `Semantic Versioning`을 함께 사용한다.

## 왜 중요한가

버전이 없으면 "지금 운영 중인 코드가 무엇인지", "언제 어떤 기능이 들어갔는지", "어느 시점부터 장애가 났는지"를 추적하기 어렵다. 배포 자동화, 롤백, 공지, 협업 모두 버전 체계 위에서 정리된다.

- 운영 중인 배포본을 정확히 식별할 수 있다.
- 릴리스 단위로 변경 내용을 정리할 수 있다.
- 문제 발생 시 어느 버전에서 깨졌는지 추적하기 쉽다.
- 팀원끼리 같은 기준으로 배포와 롤백을 이야기할 수 있다.

## 1. 가장 기본 개념

### 버전

- 보통 `v1.2.3` 같은 형식으로 쓴다.
- 앞의 `v`는 관례이며, 붙여도 되고 안 붙여도 되지만 팀에서 통일해야 한다.

### 태그

- 특정 커밋에 버전 이름을 붙이는 것이다.
- 예: `v1.0.0` 태그는 "이 커밋이 1.0.0 릴리스 기준점"이라는 뜻이다.

### 릴리스

- 태그를 기준으로 GitHub에서 배포 기록을 정리한 것이다.
- 보통 릴리스 노트, 주요 변경점, 배포 대상 정보를 함께 남긴다.

## 2. Semantic Versioning

가장 많이 쓰는 방식은 `MAJOR.MINOR.PATCH`다.

- `MAJOR`: 하위 호환이 깨지는 큰 변경
- `MINOR`: 하위 호환은 유지되지만 기능이 추가된 변경
- `PATCH`: 버그 수정이나 작은 변경

예시:

- `1.0.0`: 첫 안정 버전
- `1.1.0`: 기능 추가
- `1.1.1`: 버그 수정
- `2.0.0`: API나 동작 방식이 바뀌어 호환이 깨짐

## 3. 언제 버전을 올리는가

### PATCH를 올리는 경우

- 버그 수정
- 문구 수정
- 성능 개선
- 동작은 같고 안정성만 개선한 경우

### MINOR를 올리는 경우

- 새 기능 추가
- 기존 기능을 확장했지만 호환성은 유지되는 경우
- 관리자 페이지나 API가 추가된 경우

### MAJOR를 올리는 경우

- API 응답 형식이 깨지는 변경
- 프론트와 백엔드 계약이 달라지는 변경
- 기존 사용법을 더 이상 유지할 수 없는 구조 변경

## 4. 버전을 어떻게 설정하는가

버저닝에서 가장 중요한 것은 "이번 변경이 어느 정도 크기인지"를 팀이 같은 기준으로 판단하는 것이다. 그냥 감으로 올리면 나중에 버전 숫자가 아무 의미가 없어지기 쉽다.

### 시작 버전은 어떻게 잡는가

- 아직 외부 사용자에게 안정적으로 제공하지 않는 초기 개발 단계면 `v0.1.0`부터 시작한다.
- 내부 테스트만 가능한 수준이면 `v0.x.x` 구간을 유지한다.
- 외부 공개 또는 운영 안정성을 어느 정도 보장할 수 있는 시점에 `v1.0.0`으로 올린다.

### 이 프로젝트에서 권장하는 시작 방식

- 첫 개발 시작: `v0.1.0`
- 핵심 티켓팅 흐름이 동작: `v0.2.0`
- 티켓 검증, 운영 기본 기능 포함: `v0.3.0`
- 내부 운영 안정화 완료: `v1.0.0`

### 어떤 숫자를 올릴지 판단하는 순서

1. 기존 사용자나 클라이언트가 깨지는가
2. 새로운 기능이 추가되었는가
3. 기능 변화 없이 수정만 들어갔는가

판단 규칙은 단순하게 가져가는 것이 좋다.

- 기존 계약이 깨지면 `MAJOR`
- 계약은 유지되고 기능이 늘어나면 `MINOR`
- 기능 변화 없이 수정이나 안정화면 `PATCH`

### 이 프로젝트 기준 예시

- SSE 연결 누수 수정, 문구 수정, 성능 튜닝: `PATCH`
- 티켓 검증 화면 추가, 관리자 기능 추가, 새로운 실험 UI 추가: `MINOR`
- API 응답 구조 변경, 티켓팅 상태 값 변경, 프론트가 반드시 수정되어야 하는 계약 변경: `MAJOR`

### pre-release를 써야 하는 경우

- 운영 전 검증이 필요한 빌드는 `v0.4.0-rc.1`, `v1.0.0-beta.1`처럼 표기할 수 있다.
- 카나리 배포나 사전 검증 단계에서는 정식 릴리스 전에 pre-release를 쓰는 편이 추적에 유리하다.
- 단, 팀이 pre-release 규칙을 명확히 정하지 않았다면 너무 복잡하게 쓰지 않는 것이 낫다.

## 5. GitHub에서 실제로 어떻게 쓰는가

### 기본 흐름

1. 기능 개발과 리뷰를 마친다.
2. 배포 가능한 커밋을 기준으로 버전을 정한다.
3. 해당 커밋에 태그를 만든다.
4. GitHub Release를 생성해 변경 사항을 정리한다.
5. CI/CD는 이 태그나 릴리스를 기준으로 배포할 수 있다.

버전 설정은 `GitHub 웹 UI`로도 할 수 있고, `CLI`로도 할 수 있다. 팀에서 둘 중 하나를 표준으로 정해 쓰면 된다.

### 방법 1. GitHub 웹에서 실제로 버전 설정하는 방법

1. 배포 기준이 될 커밋이 `main` 또는 배포 브랜치에 머지되어 있는지 확인한다.
2. GitHub 저장소의 `Releases` 메뉴로 들어간다.
3. `Draft a new release`를 누른다.
4. `Choose a tag`에서 새 버전 이름을 입력한다.
5. 예: `v0.3.0`, `v1.0.0`
6. 기존 태그가 없으면 `Create new tag`를 선택한다.
7. 어떤 브랜치 또는 커밋을 기준으로 태그를 만들지 선택한다.
8. Release title에는 보통 태그와 같은 버전 또는 배포 이름을 적는다.
9. Release notes에는 이번 버전에서 바뀐 내용을 요약한다.
10. 초안 저장은 `Save draft`, 정식 공개는 `Publish release`를 누른다.

즉, GitHub 웹에서는 보통 `Release를 만들면서 tag를 같이 생성`하는 방식으로 버전을 설정한다.

### 방법 2. CLI로 실제 버전 설정하는 방법

#### `git`만 사용하는 방법

1. 배포 기준 커밋을 최신 상태로 맞춘다.
2. 로컬에서 태그를 만든다.
3. 태그를 원격 저장소로 push한다.
4. 필요하면 GitHub `Releases` 화면에서 해당 태그 기준으로 릴리스를 만든다.

가장 기본적인 명령은 아래와 같다.

- 태그 생성: `git tag v0.3.0`
- 주석 태그 생성: `git tag -a v0.3.0 -m "Release v0.3.0"`
- 태그 push: `git push origin v0.3.0`
- 모든 태그 push: `git push origin --tags`

실무에서는 가볍게 이름만 붙이는 태그보다, 설명이 남는 `annotated tag`를 더 많이 쓴다.

#### `gh`까지 사용하는 방법

- `gh` CLI를 쓰면 릴리스까지 명령어로 바로 만들 수 있다.
- 즉, `git`은 태그를 만들고 `gh`는 GitHub Release를 생성하는 데 쓴다.

예시 흐름:

- 태그 생성: `git tag -a v0.3.0 -m "Release v0.3.0"`
- 태그 push: `git push origin v0.3.0`
- 릴리스 생성: `gh release create v0.3.0 --title "v0.3.0" --notes "변경 내용 요약"`

즉, CLI에서는 `git`만 써도 태그 기준 버전 관리는 가능하고, `gh`까지 쓰면 GitHub Release까지 한 번에 정리할 수 있다.

### 어떤 커밋에 버전을 붙여야 하는가

- 반드시 "배포 가능한 상태"의 커밋에만 붙여야 한다.
- 개발 중간 커밋이나 테스트가 덜 끝난 커밋에 붙이면 안 된다.
- 보통은 PR 머지 후 `main`의 특정 커밋에 붙인다.
- 카나리 배포라면 카나리 대상 커밋에도 별도 버전을 붙여 추적 가능하게 만든다.

### GitHub에서 자주 하는 실수

- 브랜치 이름만 보고 버전이 정해졌다고 생각하는 것
- 릴리스는 만들었는데 실제 태그 기준 커밋을 확인하지 않는 것
- `latest`만 보고 운영 버전을 추적하려는 것
- 태그를 덮어쓰거나 같은 버전 이름을 다시 쓰는 것

한 번 공개한 버전 태그는 되도록 재사용하지 않는 것이 맞다.

### 왜 태그와 릴리스를 같이 쓰는가

- 태그는 기준점이고
- 릴리스는 사람이 읽는 배포 기록이다.

태그만 있으면 기계적으로는 충분할 수 있지만, 실무에서는 어떤 변경이 들어갔는지 설명이 남아야 운영과 협업이 편해진다.

## 6. 브랜치와 버전의 관계

- `main` 또는 `release` 브랜치에서 배포 가능한 상태를 유지한다.
- 실제 운영 배포는 특정 브랜치가 아니라 특정 태그 기준으로 하는 것이 안전하다.
- 브랜치는 계속 움직이지만, 태그는 고정된 기준점이기 때문이다.

즉, "운영은 `main` 브랜치"가 아니라 "운영은 `v1.3.2` 태그"처럼 말할 수 있어야 한다.

## 7. 이 프로젝트에서 권장하는 방식

- 버전 형식은 `vMAJOR.MINOR.PATCH`를 사용
- 운영 배포는 브랜치가 아니라 태그 기준으로 관리
- GitHub Release에 주요 변경 사항을 요약
- 카나리 배포 대상도 버전 기준으로 식별
- 장애 발생 시 어떤 버전이 어느 비율로 배포되었는지 추적 가능해야 함

### 버전 올림 규칙

- 버그 수정 배포: `PATCH`
- 기능 추가 배포: `MINOR`
- 프론트/백엔드 계약 변경 배포: `MAJOR`
- 아직 정식 공개 전에는 `0.x` 구간 유지
- 첫 안정 운영 기준을 만족하면 `1.0.0` 선언

### 1.0.0 기준 예시

- 티켓팅 요청, 발급, 검증의 핵심 흐름이 동작한다.
- 운영 배포와 롤백 절차가 정리되어 있다.
- 주요 장애 상황에 대한 대응 기준이 있다.
- API와 UI 계약이 당분간 크게 흔들리지 않는다.

예를 들면 아래 흐름이 자연스럽다.

- `v0.1.0`: 첫 내부 테스트 버전
- `v0.2.0`: 티켓팅 기본 흐름 추가
- `v0.2.1`: SSE 연결 안정화 수정
- `v0.3.0`: 티켓 검증 UX 실험 추가
- `v1.0.0`: 운영 가능한 첫 안정 버전

## 8. 카나리 배포와 버저닝

이 프로젝트는 카나리 배포와 A/B 테스트를 고려하므로 버전 관리가 더 중요하다.

- 카나리 배포는 "새 버전을 일부 사용자에게만 노출"하는 방식이다.
- 그래서 어떤 실험군이 어떤 버전을 보고 있는지 식별 가능해야 한다.
- `stable`과 `canary`를 말로만 구분하지 말고, 실제 버전으로 남겨야 한다.
- 장애가 나면 어떤 버전을 즉시 롤백해야 하는지 명확해야 한다.

예를 들어 `v0.4.0`은 안정 버전이고, `v0.5.0`은 카나리 대상이라면 운영 기록과 지표도 이 버전 기준으로 남겨야 한다.

## 9. 실수 패턴

- 브랜치 이름을 버전처럼 취급하는 것
- 태그 없이 그냥 최신 커밋을 배포하는 것
- 버전 규칙 없이 `final`, `real-final`, `final-v2`처럼 이름 붙이는 것
- 릴리스 노트를 남기지 않아 변경 내용을 나중에 추적 못하는 것
- 호환성 깨지는 변경인데도 PATCH나 MINOR만 올리는 것
- `0.x` 단계인데도 의미 없이 MAJOR 숫자만 올리는 것

## 10. 체크리스트

- `Semantic Versioning`의 의미를 설명할 수 있다.
- 태그와 릴리스의 차이를 이해한다.
- 운영 배포를 브랜치가 아니라 태그 기준으로 설명할 수 있다.
- PATCH, MINOR, MAJOR 중 무엇을 올려야 할지 판단할 수 있다.
- `v0.x`에서 `v1.0.0`으로 넘어가는 기준을 설명할 수 있다.
- 카나리 배포 시 어떤 버전이 어느 실험군에 들어갔는지 추적해야 하는 이유를 설명할 수 있다.
