# 3년차 체크리스트

이 문서는 "공부했다"가 아니라 "실무에서 할 수 있다" 기준으로 보는 체크리스트다.

## 이 문서를 쓰는 방법

각 항목을 볼 때 아래 기준으로 체크하면 된다.

- 안다: 용어와 개념을 설명할 수 있다.
- 해봤다: 코드나 운영에서 직접 적용해본 적이 있다.
- 맡길 수 있다: 혼자서 설계하고 문제를 해결할 수 있다.

"안다"만 많고 "해봤다"가 적으면 아직 실무 내재화가 덜 된 상태다.

## A. Kotlin

- null-safety를 설계 수준에서 다룬다.
- data class, sealed class, extension function을 적절히 쓴다.
- 가독성을 해치지 않는 선에서 Kotlin다운 표현을 선택한다.
- 예외와 결과 모델을 일관되게 다룬다.

## B. Spring

- 요청부터 응답까지 흐름을 설명할 수 있다.
- 계층별 책임을 지키면서 기능을 구현한다.
- validation, 예외 처리, 로깅을 공통 구조로 정리할 수 있다.
- 설정 분리와 프로파일 전략을 운영 환경까지 고려한다.

## C. JPA / DB

- 영속성 컨텍스트를 이해하고 있다.
- N+1과 지연 로딩 문제를 대응할 수 있다.
- 인덱스와 실행 계획의 기본 개념이 있다.
- 트랜잭션 범위를 의도적으로 설계한다.

## D. Security

- 인증 / 인가 흐름을 설명할 수 있다.
- 토큰 기반 인증의 장단점을 안다.
- 권한 체크 위치를 설계할 수 있다.
- 보안상 민감한 로그와 데이터를 구분한다.

## E. Testing

- 단위 / 슬라이스 / 통합 테스트를 구분해서 쓴다.
- 실패 케이스를 빠뜨리지 않는다.
- 테스트가 구현 세부사항에 과하게 묶이지 않게 작성한다.
- 리팩터링을 버틸 수 있는 테스트를 선호한다.

## F. 운영 / 성능

- 느린 API를 보면 DB, 외부 호출, 직렬화, 락을 의심할 수 있다.
- 캐시를 도입할 기준과 무효화 위험을 안다.
- 장애 발생 시 로그, 메트릭, 배포 이력을 함께 본다.
- 배치, 메시지, 재시도 구조의 실패 시나리오를 생각한다.

## G. 협업

- 요구사항이 모호하면 구현 전에 질문한다.
- PR 설명에 의도와 영향 범위를 적는다.
- 리뷰 피드백을 반영할 때 근거를 남긴다.
- 레거시 코드를 무조건 비난하지 않고 맥락을 본다.

## 부족한 항목을 채우는 방법

- Kotlin이 약하면: null 처리, DTO 분리, 함수 길이 줄이기를 현재 코드에서 직접 고친다.
- Spring이 약하면: 요청 흐름과 예외 처리 구조를 코드 따라가며 문장으로 설명해본다.
- JPA가 약하면: SQL 로그를 켜고 repository 메서드가 실제로 어떤 쿼리를 만드는지 본다.
- Security가 약하면: 인증 실패, 권한 실패, 만료 토큰 케이스를 직접 테스트한다.
- Testing이 약하면: 성공만 있는 테스트를 실패/예외 케이스까지 늘린다.
- 운영이 약하면: 로그, 설정, 배포 이력을 같이 보는 습관을 만든다.
