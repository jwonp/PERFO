# 3년차가 봐야 할 설계와 운영

3년차 전후부터는 "내가 구현할 수 있다"보다 "이 구조가 오래 버티는가"를 봐야 한다.

## 왜 중요한가

3년차부터는 단순 구현 속도보다 구조적 판단의 질이 더 크게 드러난다. 같은 기능을 만들어도 어떤 경계를 두고, 어떤 실패를 미리 막고, 운영에서 어떻게 추적 가능하게 두느냐에 따라 팀 생산성이 크게 달라진다.

## 먼저 알아둘 용어

- 도메인 경계: 서로 다른 비즈니스 책임이 섞이지 않도록 나누는 경계다.
- 모듈 분리: 관련 있는 코드끼리 묶고, 관계없는 코드는 떨어뜨려 두는 구조화 방식이다.
- 응집도: 하나의 모듈이나 클래스가 얼마나 한 가지 목적에 집중하는지를 뜻한다.
- 결합도: 서로 다른 모듈이 얼마나 강하게 의존하는지를 뜻한다.
- 유스케이스: 사용자가 시스템으로 수행하려는 하나의 목적 있는 작업 흐름이다.
- 일관성(consistency): 데이터가 기대한 규칙과 상태를 계속 유지하는 성질이다.
- observability: 시스템 내부 상태를 로그, 메트릭, 트레이싱으로 관찰 가능한 상태를 뜻한다.
- idempotency: 같은 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 같게 유지되는 성질이다.

## 1. 계층형 구조를 넘어서기

단순 CRUD가 아닌 순간부터 아래를 고민해야 한다.

- 도메인 경계
- 모듈 분리
- 서비스 책임 분산
- 외부 시스템 연동 책임

### 용어 설명

- 서비스 책임 분산: 하나의 서비스 클래스가 모든 일을 하지 않도록 유스케이스 기준으로 나누는 것이다.
- 외부 시스템 연동: DB 외부의 Redis, Kafka, 이메일, 결제, 파일 스토리지 등과 통신하는 작업이다.

### 봐야 하는 신호

- 하나의 Service가 너무 많은 유스케이스를 가짐
- Repository 호출이 여러 서비스에 중복됨
- DTO 변환 코드가 군데군데 흩어짐

### 어떻게 개선하는가

- 유스케이스 기준으로 서비스를 다시 나눈다.
- 반복되는 변환 로직은 mapper나 조립 지점으로 모은다.
- 외부 시스템 연동은 서비스 본문 깊숙이 넣기보다 별도 협력 객체로 분리한다.

## 2. 설계 원칙

- 응집도 높게, 결합도 낮게
- 변경 이유가 다른 코드는 분리
- 인터페이스는 필요할 때만 도입
- 공통화는 중복을 몇 번 본 뒤에 한다

### 용어 설명

- 응집도 높게: 관련 있는 로직이 한곳에 모여 있어 수정 이유가 명확한 상태다.
- 결합도 낮게: 한 부분을 바꿔도 다른 부분에 영향이 최소화되는 상태다.
- 인터페이스: 구현체를 추상화해서 교체 가능성을 열어두는 타입이다.
- 공통화: 반복되는 코드를 하나의 공통 로직으로 묶는 작업이다.

### 어떻게 판단하는가

- "이 코드가 바뀌는 이유가 같은가"를 기준으로 묶는다.
- 아직 구현체가 하나이고 교체 가능성도 낮으면 인터페이스를 강제로 만들지 않는다.
- 공통화 후 읽기 어려워지면 오히려 중복보다 나빠질 수 있다.

## 3. 트랜잭션과 일관성

3년차면 단일 DB 트랜잭션만 보는 수준을 넘어서야 한다.

- 이벤트 기반 처리
- eventually consistent 구조
- outbox 패턴 개념
- 실패 재시도 전략
- 중복 처리 idempotency

Kafka나 Redis를 붙이기 시작하면 이 감각이 중요해진다.

### 용어 설명

- 이벤트 기반 처리: 직접 메서드 호출 대신 이벤트를 발행하고 다른 컴포넌트가 이를 소비해 후속 작업을 하는 방식이다.
- eventually consistent: 모든 시스템이 즉시 같은 상태는 아니어도, 시간이 지나면 최종적으로 일관된 상태에 도달하는 구조다.
- outbox 패턴: DB 저장과 이벤트 발행 사이의 불일치를 줄이기 위해, 먼저 DB에 이벤트를 안전하게 기록한 뒤 별도 프로세스로 발행하는 방식이다.
- 재시도 전략: 일시적 실패가 났을 때 몇 번, 어떤 간격으로 다시 시도할지 정하는 규칙이다.
- 중복 처리: 같은 메시지나 요청이 두 번 들어와도 중복 저장, 중복 결제 같은 문제가 나지 않게 막는 처리다.

### 어떻게 접근하는가

- 한 DB 안에서 끝나는 문제인지, 외부 시스템까지 걸친 문제인지 먼저 구분한다.
- 외부 발행과 DB 저장을 동시에 맞춰야 하면 outbox 같은 패턴을 검토한다.
- 재시도 가능한 작업인지, 중복 실행되면 위험한 작업인지 먼저 정리한다.

### 꼭 묻게 되는 질문

- 이벤트가 두 번 소비되면 안전한가
- 메시지는 갔는데 DB 반영이 실패하면 어떻게 되는가
- 반대로 DB 저장은 됐는데 메시지 발행이 실패하면 어떻게 복구할 것인가

## 4. 성능 관점

- 병목 지점 찾기
- 쿼리 튜닝 기본
- 캐시 도입 기준
- pagination 전략
- 대량 트래픽 시 락 / 경합 문제

### 용어 설명

- 병목 지점: 전체 성능을 가장 많이 느리게 만드는 구간이다.
- 캐시: 자주 쓰는 데이터를 더 빠른 저장소에 임시 저장해 반복 계산이나 조회를 줄이는 기법이다.
- pagination: 한 번에 모든 데이터를 주지 않고 페이지 단위로 나눠 조회하는 방식이다.
- 락(lock): 동시에 같은 자원에 접근할 때 충돌을 막기 위해 접근을 제한하는 장치다.
- 경합(contention): 여러 요청이 같은 자원을 동시에 사용하려고 경쟁하면서 성능이 떨어지는 상황이다.

### 실무 포인트

- 성능 최적화는 측정 전에는 가설이다.
- 감으로 Redis를 붙이지 않는다.
- 캐시 무효화 전략이 없으면 캐시는 독이 된다.

### 어떻게 진단하는가

1. 느린 구간이 API 전체인지, DB인지, 외부 호출인지 나눈다.
2. 로그와 메트릭으로 병목 위치를 좁힌다.
3. SQL 수, 실행 시간, 응답 크기, 호출 횟수를 본다.
4. 그 뒤에야 캐시나 구조 변경을 검토한다.

### 어떻게 캐시를 판단하는가

- 같은 조회가 자주 반복되는가
- 조금 늦게 반영돼도 되는 데이터인가
- 무효화 시점을 명확히 정의할 수 있는가

셋 중 하나라도 불명확하면 섣불리 캐시를 넣지 않는 편이 낫다.

## 5. 운영 관점

- 로그, 메트릭, 트레이싱
- 장애 재현 절차
- 배포 전략
- 설정값 관리
- 민감정보 관리

### 용어 설명

- 메트릭(metrics): 요청 수, 에러율, 응답 시간처럼 수치로 볼 수 있는 운영 지표다.
- 트레이싱(tracing): 하나의 요청이 여러 서비스와 계층을 어떻게 지나갔는지 추적하는 기법이다.
- 배포 전략: 새 버전을 어떤 방식으로 서비스에 반영할지에 대한 방법이다. 예: 롤링 배포, 블루-그린 배포
- 민감정보: 노출되면 보안상 문제가 되는 정보다. 예: 비밀번호, 토큰, 개인식별정보

### 최소한 할 수 있어야 하는 것

- 장애 시간대의 로그를 찾는다.
- 어떤 배포 이후 문제가 생겼는지 추적한다.
- 운영 이슈를 코드 이슈와 설정 이슈로 나눠 본다.

### 어떻게 해야 하는가

- 요청 단위 식별자나 사용자 식별 가능한 키로 로그를 묶어 본다.
- 장애 발생 시각 전후의 배포 이력과 설정 변경 이력을 같이 본다.
- 재현 가능한지, 특정 환경에서만 나는지, 특정 데이터에서만 나는지 먼저 분류한다.

## 6. 코드 리뷰와 협업

- 왜 이 구조를 택했는지 설명할 수 있어야 한다.
- 리뷰에서 취향과 설계를 구분해야 한다.
- 테스트, 예외, 롤백 가능성을 같이 본다.

### 용어 설명

- 롤백 가능성: 문제가 생겼을 때 이전 상태나 이전 버전으로 안전하게 되돌릴 수 있는지에 대한 관점이다.
- 구조적 문제: 코드 스타일이 아니라 책임 분리, 데이터 일관성, 확장성 같은 설계 수준의 문제다.

### 어떻게 리뷰하는가

- 이 변경이 시스템 경계에 어떤 영향을 주는지 본다.
- 실패 케이스와 롤백 경로가 있는지 본다.
- "나는 이렇게 안 쓴다"보다 "이 구조가 어떤 리스크를 만들 수 있는가"로 말한다.

## 7. 3년차부터 차이 나는 지점

- 단기 구현보다 유지보수 비용을 먼저 본다.
- 장애 가능성을 미리 줄이는 설계를 한다.
- 미래 확장보다 현재 문제 정의를 정확히 한다.
- 시스템 전체 흐름을 설명할 수 있다.

## 지금 당장 해볼 것

1. 현재 서비스 하나를 골라 책임이 과한지 점검한다.
2. API 하나의 병목이 생기면 어디부터 볼지 순서를 적어본다.
3. Redis나 Kafka를 붙일 경우 실패 시나리오를 먼저 써본다.
4. 최근 작성한 PR을 보고 구조 선택 이유가 설명 가능한지 점검한다.

## 체크리스트

- 서비스 경계와 책임 분리를 설명할 수 있다.
- 캐시 도입 전후의 trade-off를 말할 수 있다.
- 이벤트 기반 처리의 장단점을 안다.
- 장애 원인 분석을 로그와 지표로 접근할 수 있다.
- 코드 리뷰에서 구조적 문제를 짚을 수 있다.
