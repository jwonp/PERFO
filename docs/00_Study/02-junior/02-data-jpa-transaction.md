# JPA, DB, 트랜잭션

많은 주니어가 여기서 막힌다. CRUD는 되는데, 왜 느린지 왜 꼬이는지 왜 데이터가 이상한지 설명을 못 한다. 이 문서는 그 구간을 메우기 위한 것이다.

## 왜 중요한가

실무 데이터 문제는 대부분 JPA를 몰라서라기보다, JPA가 DB와 트랜잭션 위에서 어떻게 동작하는지 감이 없어서 생긴다. 이 문서의 목표는 "JPA를 쓴다"가 아니라 "무슨 SQL이 나가고 왜 그런 결과가 나오는지 설명할 수 있다"까지 가는 것이다.

## 1. SQL이 먼저다

JPA를 쓰더라도 SQL을 읽을 수 있어야 한다.

- 어떤 쿼리가 실제로 나가는지 확인
- 조인이 몇 번 일어나는지 파악
- where 조건과 인덱스 영향을 생각

### 어떻게 해야 하는가

- JPA 메서드를 작성했으면 끝내지 말고 실제 실행 SQL 로그를 본다.
- 느린 조회가 있으면 객체 그래프보다 SQL부터 본다.
- "엔티티를 가져온다"가 아니라 "결국 어떤 select가 몇 번 나가는가"로 생각한다.

## 2. JPA 핵심 개념

- Entity
- 영속성 컨텍스트
- 1차 캐시
- dirty checking
- flush
- clear

### 반드시 이해할 것

- "변경 감지로 update가 나간다"는 말의 의미
- save를 안 불러도 update 되는 이유
- 트랜잭션 안과 밖의 차이

### 어떻게 이해하면 되는가

- 트랜잭션 안에서 조회한 엔티티는 영속성 컨텍스트가 관리한다.
- 관리 중인 엔티티의 필드를 바꾸면, 커밋 시점에 JPA가 바뀐 부분을 감지해 update SQL을 만든다.
- 반대로 트랜잭션 밖이거나 detach 상태면 변경을 해도 반영되지 않는다.

### 실무에서 확인하는 방법

- 서비스 메서드에 `@Transactional`이 있는지 본다.
- 같은 엔티티를 조회 후 수정했을 때 save 호출이 꼭 필요한지 상황을 구분한다.
- 테스트에서 SQL 로그를 켜고 flush 시점이 언제인지 본다.

## 3. 연관관계 매핑

- `@OneToMany`
- `@ManyToOne`
- `@OneToOne`
- 주인 개념
- 지연 로딩과 즉시 로딩

### 실무 포인트

- 기본은 지연 로딩으로 시작한다.
- 양방향 매핑은 꼭 필요할 때만 쓴다.
- 무한 참조와 N+1 문제를 항상 경계한다.

### 어떻게 설계하는가

- 다대일 쪽이 보통 연관관계 주인이 되므로, 먼저 `@ManyToOne` 단방향으로 시작한다.
- 컬렉션이 꼭 필요한 유스케이스가 생겼을 때만 `@OneToMany`를 추가한다.
- API 응답에서 연관 엔티티를 그대로 직렬화하지 않는다. DTO로 필요한 값만 꺼낸다.

### 무엇을 조심해야 하는가

- 양방향 매핑 후 양쪽 값을 둘 다 맞춰주지 않으면 메모리 상태와 DB 반영 의도가 어긋날 수 있다.
- 직렬화 과정에서 Lazy 프록시가 터질 수 있다.
- 목록 조회에서 연관 엔티티를 루프 돌며 접근하면 N+1이 생긴다.

## 4. 트랜잭션

- ACID
- `@Transactional`
- readOnly 옵션
- 트랜잭션 전파 기본 감각

### 알아야 하는 질문

- 왜 서비스 계층에 `@Transactional`을 두는가
- readOnly 트랜잭션은 언제 쓰는가
- 같은 메서드 내부 self-invocation에서 왜 주의가 필요한가

### 어떻게 적용하는가

- 하나의 유스케이스가 성공 또는 실패로 같이 묶여야 하면 서비스 메서드에 트랜잭션을 둔다.
- 조회 전용이면 `readOnly = true`를 검토한다.
- 트랜잭션 메서드를 같은 클래스 내부에서 직접 호출하면 프록시를 못 타는 경우가 있으므로 구조를 다시 본다.

### 판단 기준

- 회원가입: 사용자 저장, 권한 저장, 부가 정보 저장이 함께 성공해야 하면 하나의 트랜잭션 후보다.
- 조회 API: 단순 조회면 readOnly 후보다.
- 외부 API 호출이 포함되면 트랜잭션을 길게 끌지 않도록 경계를 재검토한다.

## 5. 성능 문제

### 대표 문제

- N+1
- 불필요한 flush
- 큰 트랜잭션
- 인덱스 없는 조회

### 대응

- fetch join
- EntityGraph
- 필요한 컬럼만 조회하는 DTO projection
- 페이지네이션

### 각각 언제 쓰는가

- fetch join: 연관 엔티티를 함께 읽어야 하고 건수가 과하지 않을 때
- EntityGraph: 조회 전략을 선언적으로 조정하고 싶을 때
- DTO projection: 엔티티 전체가 아니라 화면/응답에 필요한 값만 가져오면 될 때
- 페이지네이션: 목록성 조회에서 기본값처럼 고려해야 한다

### 어떻게 진단하는가

- 응답이 느리면 SQL 개수와 실행 시간을 본다.
- 쿼리 수가 비정상적으로 많으면 N+1을 의심한다.
- 단건 조회는 빠른데 목록 조회만 느리면 연관 데이터 접근 패턴을 본다.

## 6. DB 설계 감각

- nullable 컬럼을 무분별하게 두지 않는다.
- unique 제약조건을 활용한다.
- 애플리케이션 validation만 믿지 않고 DB 제약도 둔다.

### 어떻게 해야 하는가

- "이 값은 정말 없어도 되는가"를 비즈니스 기준으로 먼저 묻는다.
- 중복되면 안 되는 값은 애플리케이션 검사와 DB unique를 함께 둔다.
- FK와 인덱스는 조회 패턴 기준으로 검토한다.

## 7. 실무에서 많이 하는 실수

- 엔티티를 API 응답으로 직접 반환
- 트랜잭션 범위를 너무 넓게 잡음
- Lazy loading 예외 원인 모름
- 테스트에서는 되는데 운영에서는 느린 이유를 모름

## 지금 당장 해볼 것

1. 현재 프로젝트의 repository 메서드 하나를 골라 실제 SQL이 어떻게 나갈지 예측해본다.
2. 서비스 메서드의 `@Transactional` 위치가 유스케이스 기준으로 적절한지 본다.
3. 목록 조회 코드에서 루프 안의 연관 객체 접근이 있는지 찾는다.
4. 응답 DTO가 아니라 엔티티를 직접 반환하는 코드가 있는지 찾는다.

## 체크리스트

- 영속성 컨텍스트와 dirty checking을 설명할 수 있다.
- 지연 로딩과 즉시 로딩 차이를 안다.
- N+1 문제를 인지하고 대응할 수 있다.
- 서비스 계층 트랜잭션 경계를 설계할 수 있다.
- JPA를 써도 SQL을 읽고 분석할 수 있다.
