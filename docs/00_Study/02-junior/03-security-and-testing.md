# 인증, 인가, 테스트

실무에서 기능 구현만큼 중요한 것이 "믿을 수 있는가"다. 인증과 테스트는 신뢰를 만드는 핵심이다.

## 왜 중요한가

인증과 테스트는 둘 다 "문제가 생겼을 때 어디까지 믿을 수 있는가"와 연결된다. 인증이 흔들리면 보안 사고가 나고, 테스트가 없으면 수정할 때마다 서비스가 불안해진다.

## 먼저 알아둘 용어

- 인증(Authentication): 사용자가 누구인지 확인하는 과정이다.
- 인가(Authorization): 인증된 사용자가 무엇을 할 수 있는지 판단하는 과정이다.
- Spring Security: Spring에서 인증, 인가, 보안 필터 처리를 담당하는 프레임워크다.
- Filter: 컨트롤러 전에 요청을 가로채 공통 처리를 하는 구성 요소다.
- JWT: JSON Web Token의 약자다. 로그인 정보를 서명된 토큰에 담아 주고받는 방식이다.
- 세션(Session): 서버가 로그인 상태를 저장하고 관리하는 방식이다.
- mock: 테스트에서 실제 객체 대신 동작을 흉내 내는 가짜 객체다.
- stub: 호출에 대해 미리 정한 값을 돌려주도록 만든 테스트용 대체 객체다.

## 1. Spring Security 기본

- Security Filter Chain
- 인증과 인가 흐름
- `UserDetailsService`의 역할
- PasswordEncoder
- 인증 실패와 인가 실패 차이

### 용어 설명

- Security Filter Chain: Spring Security가 요청마다 순서대로 실행하는 보안 필터 묶음이다.
- `UserDetailsService`: 사용자 정보를 조회해 인증에 필요한 형태로 넘겨주는 역할을 한다.
- PasswordEncoder: 비밀번호를 평문이 아니라 해시 형태로 저장하고 비교하기 위한 컴포넌트다.
- 인증 실패: 로그인 자체가 성립하지 않은 상태다.
- 인가 실패: 로그인은 됐지만 권한이 부족한 상태다.

### 이해해야 하는 것

- `401 Unauthorized`와 `403 Forbidden` 차이
- 로그인 성공 후 어떤 정보를 어디에 저장하는지
- 토큰 기반 인증을 붙일 때 필터가 어디서 동작하는지

### 어떻게 공부하면 되는가

- Security 설정 클래스에서 필터 체인을 먼저 읽는다.
- 요청이 들어왔을 때 어떤 필터를 통과하는지 순서를 본다.
- 인증 실패와 권한 실패가 각각 어디서 발생하는지 로그와 함께 확인한다.

## 2. JWT / 세션 감각

- Access Token
- Refresh Token
- 만료와 재발급 전략
- 로그아웃 처리 방식

### 용어 설명

- Access Token: 실제 API 호출 시 사용자 인증 정보를 담아 보내는 짧은 수명의 토큰이다.
- Refresh Token: Access Token이 만료됐을 때 새 토큰을 발급받기 위한 비교적 긴 수명의 토큰이다.
- 만료(expiration): 토큰을 더 이상 신뢰하지 않도록 하는 시간 제한이다.
- 재발급: Refresh Token 등을 이용해 새로운 Access Token을 다시 만드는 과정이다.

### 실무 포인트

- JWT는 상태가 없지만 로그아웃과 강제 만료가 어려워진다.
- Refresh Token 저장소를 어떻게 둘지 고민해야 한다.

### 어떻게 선택하는가

- 단순 서버 렌더링/전통 웹이면 세션 기반이 관리하기 쉬운 경우가 많다.
- 모바일, SPA, 여러 클라이언트가 섞이면 토큰 기반이 유리할 수 있다.
- 어떤 방식을 쓰든 만료, 재발급, 탈취 대응을 같이 설계해야 한다.

## 3. 테스트 전략

### 기본 분류

- 단위 테스트
- 슬라이스 테스트
- 통합 테스트

### 용어 설명

- 단위 테스트: 함수나 클래스 하나 수준에서 빠르게 검증하는 테스트다.
- 슬라이스 테스트: 컨트롤러나 JPA처럼 일부 계층만 잘라서 검증하는 테스트다.
- 통합 테스트: 여러 계층과 실제 인프라를 함께 연결해 전체 흐름을 검증하는 테스트다.

### 백엔드 기준 예시

- Service 테스트: 비즈니스 로직 검증
- Controller 테스트: 요청 / 응답 / validation 검증
- Repository 테스트: JPA 매핑과 쿼리 확인

### 어떻게 나누는가

- Service 테스트는 의존성을 mock으로 두고 규칙 판단이 맞는지 본다.
- Controller 테스트는 HTTP 입력과 응답 코드, validation 오류를 본다.
- Repository 테스트는 실제 DB 상호작용과 쿼리 결과를 확인한다.

## 4. 테스트에서 꼭 알아야 하는 것

- given / when / then
- mock과 stub 차이 감각
- 무엇을 mock하고 무엇을 실제로 검증할지
- 테스트는 한 가지 이유로만 실패하게 작성

### 용어 설명

- given / when / then: 테스트를 준비, 실행, 검증 단계로 나누어 읽기 쉽게 만드는 구조다.
- fixture: 테스트에서 반복해서 쓰는 데이터 세트나 객체 생성 코드다.
- 검증 포인트(assertion): 테스트가 최종적으로 확인하고 싶은 조건이다.

### 어떻게 작성하는가

- given: 어떤 상태인지
- when: 무엇을 실행하는지
- then: 무엇이 보장되어야 하는지

검증 포인트가 여러 개면 테스트도 여러 개로 나누는 편이 유지보수에 좋다.

## 5. 좋은 테스트의 조건

- 읽기 쉬움
- 재현 가능함
- 외부 환경 영향이 적음
- 검증 포인트가 분명함

### 어떻게 판단하는가

- 테스트 이름만 보고 시나리오를 이해할 수 있는가
- 실패했을 때 무엇이 깨졌는지 바로 드러나는가
- 구현 변경이 있어도 요구사항이 같으면 테스트가 살아남는가

## 6. 주니어가 자주 하는 실수

- 성공 케이스만 테스트함
- 예외 케이스를 안 씀
- 구현 세부사항만 검증하고 결과를 안 봄
- 너무 많은 것을 한 테스트에 넣음

### 어떻게 피하는가

- 각 기능마다 성공, 실패, 예외를 최소 1개씩 먼저 적는다.
- "메서드가 호출됐다"보다 "사용자 입장에서 어떤 결과가 나왔는가"를 검증한다.
- 테스트 데이터 생성이 복잡하면 fixture/helper를 도입하되 과하게 추상화하지 않는다.

## 7. 지금 프로젝트에서 특히 중요한 테스트

- 회원가입 / 로그인 성공, 실패
- validation 실패
- 권한 없는 사용자 접근
- 서비스 예외 처리
- Repository 조회 조건

## 지금 당장 해볼 것

1. Auth 관련 테스트를 성공/실패/예외 기준으로 분류해 빈 케이스를 찾는다.
2. `401`과 `403` 테스트가 분리되어 있는지 확인한다.
3. Controller 테스트가 validation을 실제로 잡아주는지 본다.
4. Service 테스트가 비즈니스 규칙을 설명하는 문서 역할을 하는지 읽어본다.

## 체크리스트

- 인증과 인가 차이를 말할 수 있다.
- `401`과 `403`을 구분해서 응답 설계할 수 있다.
- 서비스 테스트와 컨트롤러 테스트 차이를 안다.
- 성공 / 실패 / 예외 케이스 테스트를 작성할 수 있다.
- 테스트가 깨졌을 때 원인을 빠르게 좁힐 수 있다.
