# Spring 핵심 구조

주니어 단계에서는 "어노테이션 외우기"가 아니라 요청이 들어와서 DB 작업 후 응답으로 나가기까지의 흐름을 머릿속에 그릴 수 있어야 한다.

## 왜 중요한가

Spring을 제대로 이해하지 못하면 계층 책임이 무너지고, 컨트롤러가 비대해지고, 예외 처리와 설정이 중구난방이 된다. 이 문서는 "Spring이 알아서 해준다"를 넘어서 "무엇을 Spring에 맡기고 무엇을 내가 설계해야 하는가"를 정리하기 위한 것이다.

## 1. Spring Boot 기본 구조

### 알아야 하는 계층

- Controller
- Service
- Repository
- Entity
- DTO

### 각 계층 책임

- Controller: HTTP 요청 / 응답 처리
- Service: 비즈니스 로직
- Repository: DB 접근

서비스에 들어가야 할 책임과 컨트롤러에 들어가면 안 되는 책임을 구분해야 한다.

### 어떻게 나누는가

- Controller는 요청 파싱, 응답 반환, validation 진입점까지만 담당한다.
- Service는 유스케이스를 수행하고 예외를 판단한다.
- Repository는 조회/저장 규칙을 캡슐화한다.

컨트롤러에서 엔티티를 직접 조작하거나, 서비스에서 HTTP 세부사항을 알기 시작하면 경계가 무너진 신호다.

## 2. DI와 Bean

- Bean이 무엇인지
- Spring Container가 무엇인지
- 생성자 주입을 왜 쓰는지
- `@Component`, `@Service`, `@Repository`, `@RestController`

### 실무 포인트

- 필드 주입보다 생성자 주입을 우선한다.
- 의존성 개수가 많아지면 설계 신호로 본다.

### 왜 생성자 주입인가

- 객체가 생성될 때 필요한 의존성이 명확해진다.
- 테스트에서 직접 주입하기 쉽다.
- null 상태나 순환 참조를 더 빨리 드러낸다.

## 3. 요청 처리 흐름

- DispatcherServlet
- Handler Mapping
- Argument Resolver
- JSON 직렬화 / 역직렬화
- 예외 처리

최소한 "클라이언트 요청이 컨트롤러 메서드 파라미터로 어떻게 들어오는가"를 설명할 수 있어야 한다.

### 어떻게 이해하면 되는가

1. 클라이언트가 HTTP 요청을 보낸다.
2. DispatcherServlet이 어떤 컨트롤러 메서드로 보낼지 찾는다.
3. 파라미터를 `@PathVariable`, `@RequestParam`, `@RequestBody` 규칙에 따라 변환한다.
4. 컨트롤러가 서비스를 호출한다.
5. 반환값은 JSON으로 직렬화되어 응답으로 나간다.
6. 중간에 예외가 나면 예외 처리기로 전달된다.

## 4. 설정과 프로파일

- `application.yml`
- 환경별 설정 분리
- `@ConfigurationProperties`
- dev / test / prod 프로파일

### 어떻게 관리하는가

- 하드코딩 대신 설정값을 외부로 뺀다.
- 환경별로 달라지는 값만 profile별 파일로 분리한다.
- 코드 곳곳에서 `@Value`를 흩뿌리기보다 설정 클래스로 묶는 편이 유지보수에 좋다.

## 5. Validation

- `@Valid`
- `@NotBlank`, `@Email`, `@Size`
- 요청 DTO 검증
- validation 실패 응답 구조

### 어떻게 적용하는가

- 컨트롤러 진입 DTO에서 1차 검증을 한다.
- 비즈니스 규칙은 서비스에서 다시 검증한다.
- "형식 오류"와 "비즈니스 규칙 위반"은 같은 실패라도 의미가 다르므로 응답도 구분한다.

## 6. 예외 처리

- `@ControllerAdvice`
- 글로벌 예외 처리
- 공통 에러 응답 포맷

### 실무 포인트

- 예외를 컨트롤러마다 따로 처리하지 않는다.
- 비즈니스 예외와 시스템 예외를 나눠야 한다.

### 어떻게 설계하는가

- `@ControllerAdvice`에서 공통 에러 응답 포맷을 관리한다.
- 서비스는 `UserAlreadyExistsException` 같은 명시적 예외를 던진다.
- 예상 가능한 예외와 예상하지 못한 예외를 분리해 로그 레벨도 다르게 가져간다.

## 7. 로깅

- 로그 레벨
- 요청 단위 로그
- 민감정보 로그 금지

### 어떻게 남기는가

- 요청 시작/종료, 핵심 비즈니스 분기, 외부 호출 실패 지점에 로그를 둔다.
- 비밀번호, 토큰, 주민번호 같은 민감정보는 로그에 남기지 않는다.
- "에러 발생" 같은 의미 없는 로그보다 식별 가능한 키와 상황을 남긴다.

## 지금 당장 해볼 것

1. 현재 컨트롤러 하나를 골라 request -> service -> repository 흐름을 따라간다.
2. validation과 비즈니스 검증이 어디서 이뤄지는지 구분해본다.
3. 공통 예외 처리와 응답 포맷이 일관적인지 확인한다.

## 체크리스트

- Controller / Service / Repository 역할을 명확히 설명할 수 있다.
- 생성자 주입을 사용하는 이유를 말할 수 있다.
- 요청 DTO validation을 적용할 수 있다.
- 글로벌 예외 처리를 구성할 수 있다.
- 설정 파일과 프로파일을 상황에 맞게 나눌 수 있다.
